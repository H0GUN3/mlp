# 원인 서비스 순위 개선: 좁은 조사·설계 범위

## 사용자 요구와 완료 조건

1. 승인된 방향: AIOps → 마이크로서비스 장애 진단 → 원인 서비스 순위 개선.
2. 기존 진단 방법 조사, 비슷한 방법론의 비교 모델 선정, 근거 있는 기존 한계 확인.
   장애를 발생시키는 fault injection과 장애를 찾는 diagnosis를 구분한다.
3. 확인한 한계에 대응하는 모델 또는 모듈을 설계한다.
4. DiagMLP의 전체 입력 처리, 핵심 MLP, GNN 교체 비교 구조 및 수치 결과를 설명한다.
5. 좁은 개선 가설, 대안 설명, 정량 평가 및 기각 기준을 도출한다.

## 과제 경계

- 시스템에 장애가 발생했다는 조건에서 후보 서비스의 원인 순위를 산출한다.
- CPU·메모리·네트워크 등 장애 종류는 평가 조건이다. 네트워크 연구로 분야를 변경하지 않는다.
- 실제 복구, 모든 원인 코드/설정의 설명, AIOps 전체 플랫폼은 범위 밖이다.
- DiagMLP와 실제 비교 backbone(Eadro/TVDiag/DeepHunt)을 중심으로 본다.
  BARO는 비학습 보조 기준이며 같은 모델 계열인 것처럼 소개하지 않는다.
- 추가 논문은 위 방법의 해석·비교 선택을 바꾸는 직접 근거에 한정한다.
- user의 “너무 광범위하게 하지마”를 우선한다.
  ulw-research/SKILL.md의 “Exhaustive coverage is the assignment”는
  스킬의 명시적 요구지만 이번 사용자의 범위 제한을 대체하지 않는다.
  전면 수집·최대 팀 확대·새 대규모 문헌 캠페인은 하지 않는다.

## 근거 구분

- 논문 저자의 수치/설명, 공개 구현의 실제 구조, 우리 복원 선택,
  로컬 개발 진단의 관측, 제안할 가설을 구별한다.
- 로컬 5epoch 성능·희소 trace·로그 한 사례를 원 DiagMLP/Eadro의 결함으로 전가하지 않는다.
- 로그 추가, 그래프 활용, MLP 공유 scorer를 미리 해답 또는 새 기여로 정하지 않는다.
- 원문 Table IV를 직접 확인하고 수치 출처와 비교 조건을 명시한다.
  모든 baseline×dataset을 전부 재실행했다고 과장하지 않는다.
- 동일 입력·구성요소 비교와 원 방법 전체 pipeline 비교는 별도 질문이다.

## DAG 및 쓰기 범위

범위 확정 → 두 독립 조사 → 주 에이전트 설계/종합 → 출처·수치 대조.

- DiagMLP 분석 child: DIAGMLP.md만 작성.
- 방법/비교군 child: METHODS.md만 작성.
- 부모: SCOPE.md, DESIGN.md, REPORT.md, VERIFY.md.

새 모델 구현·학습·튜닝·원자료 재처리·보호 평가·설치·프로젝트 커밋은 하지 않는다.
기존 frozen source/results는 읽기만 한다.
산출물은 문서이며, 설계상 성능 개선을 이미 달성한 것으로 표현하지 않는다.
