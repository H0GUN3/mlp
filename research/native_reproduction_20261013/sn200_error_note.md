# SN 복원본 오답: 확인한 것과 확인하지 못한 것

`native_error_windows.py --system SN --epochs 200` 실행과 형식 검사는
종료코드0으로 통과했다. 저장된 검증 예측과 고장 시간표만 사용했다.
원자료나 시험 예측은 읽지 않았고 모델·점수·정답을 바꾸지 않았다.

DiagMLP 복원본의 고장 구간65개를 세 초깃값에서 확인했다.
이는 **독립된 고장195건이 아니라, 같은65개 구간을 세 번 평가한 것**이다.

- 원인 선택 오답은 합계9회, 서로 다른 시간 구간으로는8개였다.
- 세 초깃값에서 모두 틀린 동일 구간은 없었다. 그렇다고 결함이 없거나
  세 모델을 합치면 반드시 맞힌다는 뜻은 아니다.
- 9회 중8회는 구간의10개 시점 모두에 고장 표시가 붙어 있었다.
  따라서 **“주로 고장 시작·끝을 조금만 포함해서 틀렸다”는 설명은
  이 결과만으로 지지되지 않는다.**
- 장애 종류로는 네트워크 지연5회, 네트워크 손실3회, CPU 부하1회였다.
  이는 오류의 분포이지, 네트워크 장애가 원인이라고 입증한 결과는 아니다.
- 원인을 맞혀도 고장 탐지 단계에서 놓친 구간이 별도로 있었다.

지금 확인한 것은 일부 오류와 학습 초깃값에 따른 차이다.
어떤 입력이나 모델 구조 때문에 틀렸는지는 아직 확정하지 않았다.
시간표에 고장 표시가 있어도 실제 관측 신호가 충분했다는 뜻은 아니다.
특히 **이 SN 결과로 RCAEval의 train-service/delay_2 오답이 원형에도
남는다고 주장할 수 없다.** 그 사건은 해당 자료의 원형 입력으로 따로 확인한다.

근거: `sn200_error_windows.json`, `sn200_verification.json`.
