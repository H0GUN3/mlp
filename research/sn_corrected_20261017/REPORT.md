# 미학습 장애 사건의 원인 서비스 진단

## 문제와 목적

장애가 발생한 뒤 관측 구간이 주어졌을 때, 12개 서비스 중 실제 원인 서비스를 찾는 문제다. 이번 평가는 같은 시스템에서 학습에 쓰지 않은 사건으로 기존 Eadro와 DiagMLP 복원본의 성능 및 실패 양상을 확인했다. 장애 탐지, 고장 종류 분류, 장애 전 예측은 평가하지 않았다.

과거 창 단위 무작위 분할 대신 36개 사건을 세 묶음으로 나눠 세 번 순환 평가했다. 매 순환은 12개 사건으로 학습, 12개로 모델 선택, 나머지 12개로 평가했다. 모든 사건은 평가에 한 번씩 포함됐다. 입력은 승인된 `inputs.npz` 중 394행만 사용했다. 보호된 169개 시험행과 미배정 1행은 열거나 디코딩하지 않았고, native raw data도 다시 읽지 않았다.

## 비교한 방법과 평가 방식

비교 대상은 기존 모달리티 인코더와 탐지·위치 진단 head를 유지한 Eadro 복원본, 같은 인코더에 서비스 위치 정보를 넣고 전역 연결(concatenation)로 결합한 수식 기반 DiagMLP 복원본, 그리고 학습 사건의 root 빈도만 쓰는 사전 기준선이다. 두 신경망은 기존 공개 구현과 논문 저자의 통합 코드 자체가 아니라 고정된 구조의 복원본이다.

사건의 장애 창별 서비스 **확률을 평균한 뒤 사건당 하나의 서비스 순위**를 만들었다. 탐지 head가 진단 순위를 막지 않으며, 정상 창은 root 순위 점수에서 제외했다. 동률은 임의의 서비스 순서로 깨지 않고 기대 credit으로 계산했다. 따라서 3개 seed의 예측 108개는 108개의 독립 사건이 아니다.

## 정량 결과

| 방법 | seed별 Top-1 | 평균 ± seed 표본 SD | seed별 Top-3 | 평균 ± seed 표본 SD |
|---|---|---:|---|---:|
| Eadro 복원본 | 13.89%, 8.33%, 5.56% | 9.26% ± 4.24% | 27.78%, 36.11%, 22.22% | 28.70% ± 6.99% |
| DiagMLP 복원본 | 30.56%, 22.22%, 22.22% | 25.00% ± 4.81% | 58.33%, 47.22%, 44.44% | 50.00% ± 7.35% |
| 사건 root 빈도 기준선 | 각 seed에서 8.33% | 8.33% | 각 seed에서 25.00% | 25.00% |

차이는 DiagMLP에서 Eadro를 뺀 값이다. 사건별 세 seed credit을 먼저 평균한 뒤 비교했다.

| 지표 | 평균 차이 | DiagMLP 승 / 동률 / 패 | recording 4개 bootstrap 95% 범위 |
|---|---:|---:|---:|
| Top-1 | +15.74%p | 12 / 22 / 2 | +9.26%p ~ +22.22%p |
| Top-3 | +21.30%p | 17 / 14 / 5 | +12.96%p ~ +29.63%p |

Bootstrap은 고정 예측을 recording 단위로 5,000회 재표집한 탐색 범위다. 네 개 recording에 조건부인 결과이며 독립 운영환경에서의 유의성이나 일반화 보장은 아니다.

오류는 고장 종류에 따라 달랐다. Top-1에서 DiagMLP와 Eadro는 CPU 부하 사건에서 각각 8.33%와 2.78%, network delay에서 둘 다 2.78%, network loss에서 각각 63.89%와 22.22%였다. recording별 DiagMLP Top-1은 11.11%에서 40.74%, Eadro는 3.70%에서 14.81%로 변동했다. 따라서 전체 평균만으로 균일한 개선이라고 볼 수 없다.

## 학습 상태, 관측, 실패

각 실행은 200 epoch까지 학습했고, validation 기준 최선 epoch는 순환별 사전 규칙으로 골랐다. 연장 조건에 해당하는 실행이 없어 400 epoch 연장은 없었으며 `budget_bound`는 모두 false였다. 순환 0, 1은 실행당 1,000 update, 순환 2는 800 update였다. 실제 학습 stage 시간 합은 Eadro 355.32초, DiagMLP 278.01초다. 실행은 CPU에서 병렬로 일부 겹쳤으므로 이 합으로 실제 총 경과시간이나 효율 우위를 주장하지 않는다.

선택 checkpoint의 사건 Top-1은 Eadro에서 학습 8.33%~100%, validation 0%~16.67%, 평가 0%~16.67%였다. DiagMLP에서는 각각 50%~100%, 8.33%~50%, 16.67%~41.67%였다. Eadro는 9개 실행 중 7개에서 epoch 1이 선택됐고, 일부 실행은 학습 손실이 내려가는데 validation 손실이 크게 악화됐다. 예를 들어 순환 0, seed 23 Eadro는 선택 checkpoint에서 학습 Top-1 100%, NLL 0.329였지만 validation Top-1 0%, NLL 6.876, joint loss 1,384.171이었다. 반대로 DiagMLP도 학습 사건을 높은 정확도로 맞힌 실행에서 validation·평가 성능이 더 낮아지는 경우가 있었다. 이는 최적화와 일반화의 문제 가능성을 보여 주지만, 충분한 수렴 여부나 특정 구조의 결함을 확정하지 않는다.

관측 감사에서는 root trace 가능 bin 3,250개 중 743개가 관측됐고, 장애 창 325개 중 100개에는 root trace가 없었다. 경계 장애 창은 37개, 완전 내부 창은 288개였다. trace 누락이 없는 12개 사건은 모두 CPU 부하였고 누락이 있는 사건은 network 장애였으므로 누락과 고장 종류가 얽혀 있다. 누락은 실패의 필요조건도 충분조건도 아니었다. 예컨대 모든 장애 창에서 root trace가 적어도 일부 관측된 CPU 사건에서도 두 모델이 놓친 사건이 있었고, root trace 전체가 없는 network loss 사건에서도 DiagMLP가 맞힌 seed가 있었다. 결측 trace는 모든 입력 모달리티가 없다는 뜻이 아니며, 비원인 후보를 피해 서비스로 간주하지 않았다.

## 판정과 다음 단계

이 평가에서 DiagMLP 복원본은 평균 Top-1과 Top-3에서 Eadro 복원본보다 높았지만, 이는 새 방법의 개선을 입증한 결과가 아니다. 두 복원본은 결합 방식 외에도 GLU, 위치 처리, 그래프 처리, dropout 설정이 달라 GNN만의 순수 인과 효과로 해석할 수 없다. 기존 95%나 창 단위 지표와 이번 사건 단위 지표를 빼서 개선량으로 계산하지 않았다.

다음 단계는 새 모델이 아니라 읽기 전용 확인 하나를 제안한다. 고정 TRAIN scaler에서 벗어난 표준화 입력값이 Eadro의 큰 held-set 손실과 같은 원본 인덱스에 나타나는지 대조한다. 이 확인은 **실행되지 않았다**. 함께 나타나더라도 원인 증명은 아니며, 개선 실험은 별도 근거와 승인 없이는 진행하지 않는다. 현 판정은 교정된 비교 평가의 완료이지, 원인 메커니즘이나 개선책의 입증이 아니다.

## 범위와 실행 이력

이 자료는 연구자가 이미 살펴본 같은 시스템의 개발 사건이다. 새 맹검 최종시험이 아니며, 알려진 root와 고장 종류의 미학습 root×종류 조합을 다룬다. 같은 recording의 사건이 학습·validation·평가에 나뉘어 있어 새 recording이나 cold-root 일반화는 검증하지 않았다. 학습 사건 prior도 각 root가 한 건씩이라 균등 동률이다. 점수 산출 단위는 고유 사건 36개이며, 3개 seed의 예측 108개를 독립 사건으로 세지 않는다. recording과 학습 환경을 공유하므로 이 36개 사건 사이의 독립성은 확립되지 않았고, recording cluster도 4개뿐이다.

초기 실행 시도 모두가 통과한 것은 아니다. R0와 R1의 최초 작업 디렉터리 실행 시도는 학습 전에 `runner.py`를 찾지 못해 exit 2로 실패했으며, 이후의 실제 fit은 성공했다. 학습 lock 명령에 불필요한 `.`을 붙인 시도도 exit 2로 실패했고, 점을 뺀 고정 명령은 exit 0과 `SELECTION_LOCKED 18`을 반환했다. 평가 중복 실행은 기존 출력 폴더 검사에서 exit 1로 멈췄다. 이후 기록을 대조해 원래 실행 세션의 exit 0 및 `EVALUATION_PASS 18`을 복구했고, 독립 검증은 exit 0과 `VERIFY_PASS 18 54`로 끝났다. 실패한 시도를 성공으로 바꾸어 기록하지 않았다. 네이티브 LSP와 프로젝트 실행 환경의 차이도 숨기지 않는다. 별도로 설정된 CLI 진단은 분석 파일에서 0 errors, 0 warnings, 0 informations를 보고했다.
