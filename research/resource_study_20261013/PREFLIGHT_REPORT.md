# 사전점검 결과 — 데이터 규모와 trace 특징 가능성

이번에 한 일은 읽기 전용 사전점검이다. 기존 원자료·분할·모델을 변경하지 않았고,
새 학습·특징 묶음·다운로드·최종시험은 실행하지 않았다. 새 파일은 점검 코드와 보고서뿐이다.

## 1. 실제 자료 크기

GB=10^9B, GiB=2^30B. 다음 세 크기는 서로 다르다.

| Eadro SN+TT | 바이트 | 약 GB | 설명 |
|---|---:|---:|---|
| 바깥 다운로드 ZIP2개 | 127,676,922 | 0.128 | 압축된 배포본 |
| 현재 eadro_native 안의 모든 파일 | 1,414,806,696 | 1.415 | ZIP·풀린 파일·안쪽 압축본·부가 파일 포함 |
| 중복 배포본을 한 번만 센 논리적 원자료 payload | 2,305,204,357 | 2.305 | 추가 정상 수집 자료까지 해제했을 때의 파일 내용량 |

논리적 payload는 SN1.424GB(1.326GiB), TT0.881GB(0.820GiB)다.
앞선 해시 검수에서 SN-all/TT-all은 풀린 고장 자료와 동일했다.
그 중복본을 제거한 것이며, trace ID 중복까지 제거한 고유 관측량은 아니다.
정상 자료는 압축 상태로 저장돼 있어 논리적 크기가 현재 파일 크기보다 클 수 있다.
독립적인 고장 주입 기록은 여전히 SN36/TT81이며 용량이 이를 늘려주지 않는다.

다른 보유 자료의 **다운로드 당시 해시 검증 명세**:
- RCAEval RE2-OB/TT180: 2,888,270,116B=2.888GB(2.690GiB).
- ops-lite30 telemetry+455사례 metadata: 99,719,283B=0.100GB(0.093GiB).
이 두 자료는 원파일을 다시 열거나 stat하지 않았다. 봉인된 RCAEval 최종36건도 열지 않았다.

기존 자체 모델용 특징 NPZ는 SN135,693B, TT1,749,745B로 합계 약1.89MB다.
단, 이 특징의 정상 기준은 이전 창 분할을 따르므로 **그대로 사건 재분할하면 안 된다**.
사건별 TRAIN이 바뀌면 원 관측에서 정상 기준을 다시 계산해야 한다.

## 2. 부모–자식 연결은 있는가?

실제13개 고장 수집 파일을31.9초 동안 한 번씩 스트리밍했다.
원파일 SHA256은 기존 검수 명세와 모두 일치했다.
집계는 기존 TRAIN/validation 창에 시작점이 있는 span만 대상으로 했다.
부모·자식 시간 계산에는 선택되지 않은 창의 자식 span을 쓰지 않았다.

| 관측 항목 | SN | TT |
|---|---:|---:|
| 개발 구간 span 레코드 수 | 394,075 | 98,775 |
| 서로 다른 span ID | 70,396 | 23,171 |
| CHILD_OF 연결 중 같은 trace 안에 부모 존재 | 99.745% | 99.786% |
| 선택된 자식이 관측된 부모 span 레코드 | 247,436 | 66,374 |
| 자식 구간이 부모 밖으로 나간 연결 | 41,852 | 324 |
| 자식 시간을 단순 합산하면 음수가 되는 부모 | 32,341 | 162 |

**판정: 연결 구조를 이용한 잔여 시간 계산을 시도할 근거는 있다.
하지만 그대로 '자기 CPU 처리 시간'이라고 부를 근거는 없다.**

- 겹치는 자식 구간의 합집합을 사용해야 한다.
- 부모 밖 자식 시간은 SN 선택 연결의 약11.39%, TT0.37%다.
  경계 절단은 수치 범위를 지킬 뿐, 시계/계측의 물리적 불일치를 해결하지 않는다.
- SN에는 span.kind 태그가 없고 TT에는 client/server가 관측됐다.
  TT에는 FOLLOWS_FROM8개도 있었다. CHILD_OF만 있다고 동기 실행을 보장하지 않는다.
- 같은 ID의 재등장 비율은 레코드 기준 SN82.14%, TT76.54%다.
  이번 선택 범위의 시간·서비스·부모 연결·outcome signature 충돌 ID는0이었다.
  중복 집계 정책을 고정해야 하며 이를 독립 호출 수로 착각하면 안 된다.
- 부모의 자식 목록이 실제로 완전한지, 계측되지 않은 하위 호출이 없는지는 미확인이다.

## 3. 오류율과 p95/p99는 충분한가?

| 항목 | SN | TT |
|---|---:|---:|
| 오류 또는 상태 태그가 있는 span 레코드 | 12.73% | 99.99% |
| 명시적 error=True 레코드 | 24,898 | 10 |
| HTTP500 레코드 | 24,898 | 14 |
| 10초×서비스 칸에서 span이 없는 비율 | 23.12% | 93.00% |

태그 없음은 오류0이 아니다. TT는 상태 태그가 넓게 있지만 대부분200이므로,
필드 존재가 곧 장애 구분 신호가 충분함을 뜻하지 않는다.
SN의302는 오류라고 일괄 처리하지 않아야 한다.

중복 ID를 한 번만 셌을 때 TT의 관측된 모든10초×서비스 칸은
**서로 다른 span이10개 미만**이었다. p95/p99를 안정적인 꼬리 지연처럼
취급하기 어렵다. SN도100개 이상인 칸은99개뿐이다.
이는 실제 고유 요청 수가 아니라 span ID 수이며, 특정 표본 수가 신뢰성을
보장한다는 뜻도 아니다. 관측 수·결측·중복 정책을 함께 설계해야 한다.

## 4. 독립 최종평가 후보

- **RCAEval RE3-OB/TT:**60사건, Parquet 배포0.300GB / 원본ZIP0.433GB.
  부모span과상태코드 스키마가 문서화돼 있다. 다만 코드 수준 고장이고
  원인 서비스가 OB4개/TT2개에 집중되므로 A의 동일 분포 반복으로 단정하지 않는다.
- **GAIA MicroSS:** metric+trace+주입기록 배포 파일약3.399GB.
  새 시스템 전이 후보지만 실제 유효 사건 수·기간 교집합·라이선스 확인이 필요하다.
- **공식 OpenRCA:**335고장, 공식 설명상68GB 초과 telemetry.
  정확한ZIP 크기와 단일 서비스 정답으로 변환 가능한 수량은 미확인이다.
- RE1/RE2-SS/RE3-SS는 이번 메트릭+trace 계약에 필요한 trace가 없다.

자세한 출처·정확한 바이트·보류 이유는 `DATA_CANDIDATES.md`에 있다.
어떤 후보도 아직 최종 세트로 확정하거나 다운로드하지 않았다.
현재 Eadro 사건들은 모두 학습에 사용돼 깨끗한 새 최종 사건으로 만들 수 없다.

## 5. 이번 점검의 결론

1. 자기 처리 시간은 **조건부 검토 가능**: 부모 연결은 풍부하지만 시간 불일치·중복·비동기 해석을 먼저 정해야 한다.
2. 오류 특징은 **자료별로 다름**: 없는 태그를 정상으로 채우지 않는다.
3. TT의10초 p95/p99는 **관측이 매우 희소**해 원래 계획대로 곧바로 넣기 어렵다.
4. 새 최종 자료는 **후보는 있으나 아직 확정 불가**: A의 새 사건과 B의 새 시스템/새 고장 조건을 구분해 선택해야 한다.

검증: Pyright0 errors/0 warnings, 구간 합집합/절단/빈구간/0길이/태그 fixture 통과,
실제 감사 종료코드0. `trace_preflight.json`에 모든 집계와 파일 해시를 남겼다.
이는 특징의 성능 효과나 최종평가 독립성을 입증한 결과가 아니다.
