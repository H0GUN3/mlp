# 문제·차별성 재설계 — 공유 분석기와 관계 정보

## 현재 결정과 결론

사용자는 기존 평가 파이프라인 준비보다 **문제·차별성 재설계**를 선택했다.
이 문서는 현재 MLP를 유지해야 한다는 전제 없이 운영 문제, 선행연구,
관측 가능성과 중단 조건을 정리한다. 새 모델 구현·학습·분할·최종시험은 하지 않았다.
RCABench 확보·실제 사건 수 검수는 계속 후순위 백그라운드 작업이다.

**공유 분석기+관계 정보는 합리적인 설계 조합이지만 이미 선행연구에 있다.**
호출 방향을 사용하거나 원인과 전파 증상을 구분한다는 설명도 그 자체로 새롭지 않다.
현재 자료의 오류를 전파 혼동이라고 확정할 근거도 부족하다.
따라서 관계 모델을 새 방법으로 확정하기보다 **언제 관계 정보가 도움이 되는지,
언제 관측 부족 때문에 믿을 수 없는지**부터 확인하는 것이 우선이다.
이 역시 신규성이 확인된 주제가 아니라 다음에 검증할 좁은 문제 후보다.

## 1. 운영 문제와 관측 근거

운영자가 필요한 것은 “많이 이상한 곳”이 아니라 먼저 조사할 원인 후보다.
서비스 사이 호출로 지연이 함께 나타날 수 있지만, 공동 이상이 항상 전파를 뜻하지는 않는다.
공통 부하·공유 인프라·여러 원인·관측 누락도 비슷한 현상을 만들 수 있다.

| 현재 사실 | 지지하는 것 | 지지하지 않는 것 |
|---|---|---|
| 기존 delay_2 분석에서 train 정답보다 travel이3seed 모두 높음 | 원인 후보가 관측됐는데도 순위가 뒤집힌 사례 존재 | travel이 전파 증상이거나 그래프 부재가 오답 원인이라는 확정 |
| 해당 사례의travel→train span pair4,216개, unresolved parent483개 | 일부 호출 관계 확인 가능 | 완전한 호출 구조 또는 물리적 고장 위치 |
| SN 복원본9회 오답/8개 창,3seed 공통 오답 창 없음 | 오류와 초기화 변동 존재 | 특정 전파 기제가 반복적으로 실패한다는 증거 |
| 개발 spans의 관측된 CHILD_OF 부모 확인률 SN99.745%, TT99.786% | 관측된 연결의 해석을 시도할 수 있음 | 전체 호출 관계·자식 목록·모든 서비스의 관측이 완전함 |
| TT10초×서비스 칸93%에span없음 | 사건별 관계 문맥이 희소할 수 있음 | 원인 서비스에 다른 메트릭도 전혀 없다는 결론 |
| 중복 레코드와 부모 밖 자식 시간 존재 | 중복·시간 정합성 정책이 필요 | 단순 잔여 시간을 실제 자기 CPU 시간으로 해석 |

첫 delay_2 사례는17특징의 기존 로컬 adaptation 분석이다.
원래 DiagMLP 또는 현재 상대 MLP의 오류 기제로 바꾸어 말하지 않는다.
근거: `../native_reproduction_20261013/error_analysis.md:88–120`,
`sn200_error_note.md:1–26`, `PREFLIGHT_REPORT.md:35–77`.

현재 `ranker.py`의 문맥은 전체 서비스의 masked mean이다.
서비스 특징·마스크·coverage가 같고 연결만 달라진 상황은 구별하지 못한다.
이는 코드상 입력 정보의 한계이며, 그 한계 때문에 실제 오답이 발생했다는 측정은 아니다.

## 2. 관계를 이용해 이미 해결하려 한 방법

| 방법 | 구체적 기제 | 필요한 정보와 정답 단위 | 확인된 경계 |
|---|---|---|---|
| DéjàVu | class별 분석기와 전체 대상의 GAT·점수기를 공유. undirected FDG로 주변 문맥 집계 | 메트릭·호출/배포 관계·failure class·과거 장애 정답. 컴포넌트×지표군 순위 | 과거에 faulty 이력이 없던 unit 평가가 이미 있음. 서비스 전체 고장 제외와는 구분 |
| TraceRCA | 정상/이상 trace의 서비스 연관성과 incoming/outgoing 이상 호출 trace 수의 절대 불균형을 결합 | trace 소속·caller/callee·호출 측정·정상 참고 통계. 원인 서비스 순위, supervised root 학습 없음 | 원문은 상·하류로 동시에 전파되는 경우와 이상 탐지 의존성의 한계를 설명 |
| CIRCA | 각 메트릭이 정상 causal parents 조건에서 예상되는 값에서 벗어났는지 검사, descendant adjustment 추가 | 메트릭·architecture/call graph·지표 종류 매핑·정상 구간. 원인 metric 순위 | causal DAG·적절한 관측/정상 범위 가정. 숨은 원인과 부족한 정상 관측이 한계 |
| MicroRCA | 지연과 컨테이너/호스트 자원을 연결한 attributed directed graph에서 personalized PageRank | 서비스 쌍 응답시간·자원 메트릭·서비스/호스트 관계. 구현은 서비스 순위 출력 | 상관 가중 진단이지 실행/대기 시간의 명시적 분해는 아님. 전체 원문 평가 세부·한계는 미확인 |

공식 구현 존재는 확인했지만 이번에 실행하지 않았다.
CIRCA의 확인된 평가에는 simulation과Oracle99사건이 있으며,
이를 마이크로서비스의 대기 혼동만 분리한 벤치마크 결과라고 하지 않는다.
MicroRCA는 공식 초록의Kubernetes fault injection 평가와 코드 기제까지만 근거로 사용한다.

이 자료들은 “관계 방향을 쓰자” 또는 “원인 자체 이상과 의존성 때문에 생긴 이상을 나누자”가
이미 연구된 방향임을 보여준다. 모든 조건에서 기존 방법이 충분하다는 뜻은 아니다.
부족한 조건을 특정하지 않은 채 작은 MLP로 대체하는 것만으로는 차별성이 성립하지 않는다.

**추가로 확인한 중복:** DéjàVu §5.3.1은 사건별 FDG edge를 무작위로 제거해
학습·평가했고, 많이 제거하면 graph 집계를 쓰지 않는 대조군보다 나빠진다고 보고한다.
따라서 **“관계가 불완전하면 오히려 해롭다”는 관찰이나 단순 edge masking 실험도
새 발견으로 주장할 수 없다.** 현재 수집기에서 실제로 생기는 누락과 해당 무작위 제거는 별도 조건이다.

## 3. 후보 문제의 비교와 우선순위

| 후보 | 중요한 이유 | 선행연구 중복 | 지금의 판단 |
|---|---|---|---|
| 원인 라벨이 없던 서비스의 첫 고장 | 모든 서비스의 장애 사례를 확보하기 어려움 | DéjàVu의 unseen unit, BARO/PRISM의 비학습 접근과 직접 관련 | 별도 일반화 평가 조건으로 유지. 이것만으로 새 주제 확정하지 않음 |
| 호출 방향으로 원인/전파 증상 구분 | 원인이 아닌 상류 증상을 먼저 조사하는 비용 | TraceRCA·CIRCA가 직접 관련, DéjàVu도 의존 문맥 활용 | 관계 기반 모델의 필요성 가설. 기존 오답의 기제로는 미입증 |
| 불완전 관측에서 관계 문맥을 언제 믿을 것인가 | sparse trace·불완전 연결로 추론 근거가 사건마다 달라짐 | DéjàVu의 random edge 제거·무집계보다 악화 보고, TORAI의 blind spot 등과도 대조 필요 | **우선 문제 검증 후보.** 단순 누락 견고성 자체는 새롭지 않으며 신규 해결법을 확인한 것은 아님 |

세 번째를 우선 검토하는 이유는 현재 자료에서 관측 희소성·시간 불일치가 확인됐기 때문이다.
하지만 “희소하다”는 사실만으로 관계 기반 진단이 오진하거나,
특정 보정 방법이 효과적이라는 결론은 나오지 않는다.

### 제안하는 좁은 질문

> 장애 구간의 호출 관측이 불완전할 때, 원인 서비스 진단에
> 관계 문맥을 사용할 수 있는 사건과 근거가 부족한 사건을 구분할 수 있는가?

- 주어진 장애 구간과 서비스 후보 내 단일 원인 순위화를 대상으로 한다.
- graph가 없으면 항상 나쁘다거나, graph-free면 항상 견고하다고 가정하지 않는다.
- 완전 미지 고장·새 시스템 전이·자동 복구·모든 다중 원인을 한꺼번에 해결하려 하지 않는다.
- 현재 수집 자료의 sparse 상태를 임의의 random masking 결과와 동일시하지 않는다.
- 정상 구간에서 추정한 그래프도 실제 완전한 topology라는 정답으로 취급하지 않는다.

## 4. 기여 가설과 이를 반박할 수 있는 조건

현 단계에서는 아키텍처보다 아래 가설을 먼저 둔다.

**가설H1:** 동일한 로컬 관측과 학습 조건에서, 실제 호출 문맥이 전체 평균 문맥보다
특정 사건의 후보 순위를 더 잘 구분할 수 있다.

**가설H2:** 그 이점은 관측 수·부모 연결·시간 정합성·기간 coverage에 따라 달라지며,
이 차이를 측정 가능한 관측 품질로 설명할 수 있다.

H1/H2의 일반적 현상만 확인해도 새 연구 기여가 되는 것은 아니다.
남은 차별성 후보는 **완전한 그래프나 정답을 모르는 온라인 조건에서 측정할 수 있는
근거로 사건별 관계 사용/보류를 결정하고, 잘못된 진단을 실제로 줄이는가**다.
이 문제까지 이미 해결한 방법이 있는지, 추가 gate가 단순한 품질 임계값보다 나은지
확인하지 못하면 새 방법 개발로 넘어가지 않는다.

H1/H2가 지지될 때만, 품질이 충분한 관계를 선택적으로 쓰거나
근거가 부족하면 후보 범위를 넓히고 진단을 보류하는 방법을 설계 후보로 둔다.
attention weight 또는 softmax 값이 곧 관측 신뢰도라는 가정은 하지 않는다.
이 선택적 사용 아이디어도 기존 uncertainty/missing-observation 연구와 추가 대조해야 한다.

### 향후 검증을 재개할 때의 최소 대조

1. 동일한 원 관측에서 **자체 상태 / 전체 평균 문맥 / 실제 호출 문맥**을 구분한다.
2. 실제 관계와 방향 반전·적절한 재배선 등의 대조로,
   추가 입력·규모의 효과와 관계 자체의 효과를 분리한다.
   이런 대조의 성공도 실제 인과관계 발견의 증명은 아니다.
3. BARO·TraceRCA 등 실제 문헌 기준과 비교한다.
   metric/unit/service 출력의 변환과 방법별 고유 전처리·관측 시간을 사전에 고정한다.
4. 사건 비중첩이 기본이다. 관측 누락 조건·평가 지표·제외 규칙은 결과를 보기 전에 정한다.
   cold-root는 별도 조건이며 임의로 쉬운/유리한 사건만 고르지 않는다.
5. 순위 정확도 외에 관측 조건별 오류, 진단을 내리는 비율과 그중 오류율,
   전처리 포함 시간/메모리를 함께 본다. 학습 seed를 새로운 사건으로 세지 않는다.

위 항목은 아직 실행 계획 승인이나 새 학습 시작을 뜻하지 않는다.
현재 공개 자료에서 필요한 관측과 유효 사건을 확보할 수 있는지 먼저 판단해야 한다.

### 중단·축소 기준

- 원인/증상 혼동이라는 관측 근거가 없으면 그 기제를 해결했다고 주장하지 않는다.
- 관계를 바꾸어도 결과가 같거나 입력·용량 증가로 설명되면 방향성 기여를 주장하지 않는다.
- 관측 품질을 정답 없이 정의할 수 없거나 필요한 신호가 없으면 선택적 관계 방법을 강행하지 않는다.
- 단순한 문헌 방법이 충분하면 새 학습 모델의 필요성을 재고한다.
- 이점이 한 사건·한 seed·사후 선택 조건에만 있으면 일반적 개선으로 보고하지 않는다.
- 정확도에서 열세라는 이유만으로 비용 우위로 말을 바꾸지 않는다.
  비용을 기여로 삼으려면 사전 정의된 동등 성능과 전체 비용 근거가 필요하다.

## 5. 현재 계획에서 유지할 것과 보류할 것

**유지:** 검증된 기존 결과, 실제 문헌 비교, 고정 자료 보호,
사건 비중첩·TRAIN 전용 참조 원칙, 비용 평가3축, RCABench 후순위 검수.

**보류:** 현재 MLP를 정답으로 놓은 특징 묶음·앙상블·Set Transformer/GNN 추가,
기존3주 실험 일정의 자동 실행, SN/TT 새 산출물 생성, 새 학습·튜닝·최종시험.
기존 todo의 미완료 실험 항목은 완료된 것이 아니며 현재 실행 승인 목록도 아니다.

**이번에 끝낸 것:** 기존 근거와 선행연구를 대조하고 문제 후보·기여 가설·중단 기준을 정리했다.
**아직 정하지 못한 것:** 신규성이 입증된 최종 연구 주제, 유효한 새 방법,
실제 관측으로 확인한 관계 기여, 사용 가능한 추가 독립 사건 수.

따라서 현재 제안은 **관계 모델을 곧바로 구현하자**가 아니라
**관계 정보의 필요성과 사용 조건이 실제로 존재하는지 먼저 확인하자**다.
