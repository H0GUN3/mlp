# 최초 입력 집계 단계의 중단과 복구

첫 mapping 작업 `st_01a14e0d`는 매핑 저장 전에 validation 매칭 캐시의
JSON 메타데이터를 읽었다고 보고하고 산출물 없이 종료했다.
보고에 따르면 validation NPZ 배열, 보호 관측·예측은 열지 않았고
집계·solver·테스트도 실행하지 않았다. 이 실패를 성공으로 취급하지 않는다.
후속 benchmark는 필수 산출물 부재로 실행하지 않았고,
검증 경로도 누락을 보고했다.

사전 고정된256개, TRAIN 주입 전 빈도, 동률 cluster_id, 창 선택 해시,
solver·예산은 이 메타데이터 열람 후에도 전혀 바꾸지 않는다.
이전 JSON 열람 이력은 지우지 않는다. “전체 작업에서 validation 관련
파일을 단 한 번도 먼저 열지 않았다”는 주장은 할 수 없다.

다만 기존 프로토콜의 결정 규칙은 결과에 따라 선택할 여지가 없고,
정상 TRAIN48 로그만으로 빈도를 계산한다. 이전 작업의 메타데이터 열람
때문에 이 결정적 계산 자체가 불가능해진 것은 아니다.
새 집계 프로세스에서 TRAIN-only 읽기 경계를 설치하고 매핑을
배타 저장·해시 고정한 뒤 validation 캐시를 집계한다.
실제 top256은 TRAIN 빈도에서 독립 재계산해 검증한다.
과거 위반 기록과 새 실행의 경계 검증을 구분해 보고한다.

같은 DAG에서 mapping과 그 의존 경로만 재실행하며,
완료된1025차원 출처 조사는 재실행하지 않는다.
원본·보호 자료·solver·표현 규칙·예산 변경은 없다.

## 비용 측정 전 문서 해시 불일치

복구 집계는17.4623초에 종료했고, TRAIN 전용 top256·5사건10창 선택과
전체11,991,116행의 서비스별 보존 집계가 생성됐다. 독립 재집계도
매핑·선택·56개 서비스/파트/시기 셀의 일치를 확인했다.

후속 benchmark는 `MAPPING.md` 해시 불일치로 실제 fit 전에 종료했다
(exit1,0.1662초,140위치 모두 미실행). 주 담당이 mapping 작업에
읽기 경계가 OS 전체 감사가 아닌 명시적 캐시 로더 검사임을 정확히
설명하도록 보낸 메시지 이후 해당 문서가 갱신된 것이 원인이다.
수치 입력 세 파일은 다음 해시로 그대로다.

- mapping.json: a9bf14fd115d55c040c1d7a30b376411f722ef6ef12f3fa3eaf7f12d4f9b006a
- selection.json: 6b7be4278e61e6752aa8c65b15b7d58b76f227ee7738e4be33788b4e9af399e9
- coverage.json: 78a76b05fa54cd9b9a3cc92e15adb8e7d86f7ef39dd8a33ff1a1d10d35fd7181

검토한 현재 MAPPING.md 해시는
711c3e41334efa1c798ee47ef6606afd9aae670841db59b7ff156ef32ff41b46 이다.
이는 문서 인계의 동시 변경 문제이며 solver나 입력 표현의 실패가 아니다.
앞선 `fits/`와 `benchmark.json` 실패 산출물은 덮어쓰지 않는다.
복구 측정은 `fits_recovery/`, `benchmark_recovery.json`에 별도 기록하고,
새 코드 검사 후 동일한 고정 입력·표본·solver·예산으로만 실행한다.
기존 실제 fit은0회이므로 표본 재적합이나 성공할 때까지 재표본하는
복구가 아니다. 원형 데이터·모델·분할 변경도 없다.
