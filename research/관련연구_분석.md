# 관련 연구: 배경 → 문제 → 해결 → 결과 → 이번 연구

확인일: 2026-10-12. 아래 성능은 **각 논문 저자가 자기 실험에서 보고한 결과**다.
우리 데이터에서 재현한 수치가 아니며 논문 간 숫자를 직접 순위로 비교하지 않는다.
선정 기준은 ① 근본 원인과 연쇄 증상의 구분, ② 근거 선별, ③ 불완전한 관측자료,
④ 동일 과제에서 실행 가능한 비교 방법이다.

## 먼저 알아야 할 용어

- **장애 원인(fault):** CPU 고갈이나 네트워크 이상처럼 기능 저하를 일으키는 문제.
- **증상(anomaly):** 로그 오류 증가·응답 지연 등 관측된 변화. 원인과 같지 않다.
- **원인 진단(RCA):** 관측된 증상으로부터 원인 서비스/문제를 찾는 과정.
- **호출 관계:** 어느 서비스가 어느 서비스를 사용하는지. 장애가 실제 전파된 관계와 다르다.
- **baseline:** 같은 데이터·정답·정보 접근 조건으로 다시 실행해 비교할 방법.
  논문에 적힌 점수를 가져와 우리 점수 옆에 놓는 것이 아니다.

## 1. MicroHECL — 이미 이상 전파 연결을 선별하고 있었다

**논문:** *MicroHECL: High-Efficient Root Cause Localization in Large-Scale Microservice Systems*
— ICSE-SEIP 2021, pp.338–347.
[논문](https://arxiv.org/abs/2103.01782) ·
[공식 학회](https://2021.icse-conferences.org/details/icse-2021-Software-Engineering-in-Practice/35/MicroHECL-High-Efficient-Root-Cause-Localization-in-Large-Scale-Microservice-Systems)

- **주제·배경:** 대규모 서비스에서 사용자에게 보이는 장애의 원인을 빠르게 찾아야 한다.
  그러나 호출 그래프가 크고 정상적인 수치 변동도 많다.
- **발견한 문제:** 모든 호출을 따라가거나 단순 이상 탐지만 사용하면 관련 없는 서비스까지
  조사하고 전파된 증상을 원인으로 오인할 수 있다.
- **왜 중요한가:** 탐색 범위가 커질수록 진단 지연과 오탐이 늘어 실제 운영자가 사용할 수 없다.
- **해결 방법:** 알림이 발생한 서비스·비즈니스 지표를 출발점으로, 호출별 지연/오류/트래픽
  이상을 판별한다. 이상 전파의 반대 방향으로 추적하고 상관관계가 낮은 연결을 가지치기한다.
  도달한 후보를 초기 비즈니스 지표와의 상관관계 등으로 순위화한다.
- **결과·결론:** Alibaba 28개 하위 시스템 75건에서 HR@1 0.48, HR@3 0.67을 보고했다.
  가지치기 실험에서는 HR@3을 유지하면서 시간이 줄었다. 산업 현장 적용 가능성의 근거지만
  다른 데이터의 동일 성능을 보장하지 않는다.
- **우리 연구에 주는 의미:** “관련 없는 연결을 제거한다”나 “전파 방향을 이용한다”는
  발상 자체는 새롭지 않다.
- **baseline 가능 여부:** 전체 재현에는 초기 경보, 호출별 지표, 학습된 탐지기,
  더 긴 과거 이력이 필요하다. 확인한 범위에서 공식 공개 구현은 찾지 못했다.
  일부 규칙만 구현하면 **MicroHECL 참고 규칙**이라고 적어야 한다.

## 2. BARO — 원인 진단 전에 장애 시작 시각도 불확실하다

**논문:** *BARO: Robust Root Cause Analysis for Microservices via Multivariate Bayesian
Online Change Point Detection* — PACMSE 1, FSE 2024.
[논문](https://arxiv.org/abs/2405.09330) ·
[출판 DOI](https://doi.org/10.1145/3660805) ·
[저자 코드](https://github.com/phamquiluan/baro)

- **주제·배경:** 원인 지표를 찾을 때 정상 구간과 장애 구간의 변화를 비교한다.
- **발견한 문제:** 장애 탐지 시각이 실제 시작보다 빠르거나 늦으면 정상 기준에 장애 값이
  섞여 기존 점수의 신뢰성이 떨어진다.
- **왜 중요한가:** 실제 시스템의 탐지기는 완벽하지 않으므로, 정확한 시작 시각을
  가정한 좋은 결과가 운영에서는 무너질 수 있다.
- **해결 방법:** 다변량 베이지안 온라인 변화점 탐지로 시작 시각을 찾고,
  정상 중앙값·IQR에 기반한 RobustScorer로 변한 지표와 서비스를 순위화한다.
  서비스 호출 그래프가 없어도 동작하는 수치 기반 방법이다.
- **결과·결론:** 3개 시스템의 주입 장애 300건과 시작 시각 오차 실험으로
  강건성의 이점을 보고했다. 여기서 주입 장애는 자연 발생 운영 장애와 동일하지 않다.
- **우리 연구에 주는 의미:** 복잡한 LLM을 넣기 전에 이처럼 단순하고 강한 수치 방법을
  이겨야 한다. 주입 시각을 제공한 비교는 ‘시작 시각을 알고 하는 RCA’로 한정해야 한다.
- **baseline 가능 여부:** 우선 구현·검증할 비교 대상이다. 다만 논문의
  최대 **절댓값** 변화와 [공식 0.2.0 코드](https://github.com/phamquiluan/baro/blob/0.2.0/baro/root_cause_analysis.py)의
  **부호 있는 최댓값** 계산이 다르다. 공식 코드 버전과 전처리를 고정한다.
  시작 시각을 정답으로 제공하면 전체 BARO가 아니라 **알려진 시작 시각의 BARO 점수기**라고 명시한다.

## 3. TORAI — 호출 그래프에 안 보이는 서비스도 원인일 수 있다

**논문:** *TORAI: Multi-source Root Cause Analysis for Blind Spots in Microservice Service
Call Graph* — PACMSE 3, FSE 2026.
[논문](https://arxiv.org/html/2604.13522v1) ·
[출판 DOI](https://doi.org/10.1145/3808137) ·
[저자 코드](https://github.com/phamquiluan/RCAEval/blob/fse26/RCAEval/e2e/torai.py) ·
[고정 소스 배포](https://doi.org/10.6084/m9.figshare.31938495.v1)

- **주제·배경:** 많은 다중 관측자료 RCA 방법이 트레이스로 서비스 호출 그래프를 만든다.
- **발견한 문제:** 계측하지 않은 서비스나 닫힌 구성요소는 그래프에서 빠진다.
  또 대량 학습 정답이나 로그·트레이스의 강한 연계를 요구하는 방법은 적용하기 어렵다.
- **왜 중요한가:** 실제 원인이 후보 그래프에 없으면 뒤의 추론이 아무리 좋아도 찾을 수 없다.
- **해결 방법:** 메트릭·로그·트레이스를 시계열로 만들고 이상 심각도를 계산한다.
  유사한 증상의 서비스끼리 군집화한 뒤 군집 안에서 인과 분석을 수행하고 순위를 합친다.
  서비스 호출 그래프는 필요 없지만, 통계적인 인과 그래프 분석 자체를 안 하는 것은 아니다.
- **결과·결론:** 270건 주입 장애와 운영 장애 10건을 평가했다. 운영 10건에서
  Top-3 100%를 보고했지만 Top-1은 TORAI 60%, BARO 70%였다.
  **모든 조건에서 TORAI가 더 좋다는 결론은 틀리다.**
- **우리 연구에 주는 의미:** 관계 선별이 관측되지 않은 서비스의 근거까지 제거하면 안 된다.
  카드 전체를 유지하고 관계 정보만 바꾸는 설계가 필요한 이유다.
- **baseline 가능 여부:** 다중 관측자료 기준점으로 관련성이 높다. 하지만 제공 함수의
  hard clustering, 일부 경로에서의 데이터 사용, 거친 서비스 순위 출력 등은 논문 전체
  설명과 차이가 있다. 시간축 정렬과 누락 처리를 점검한 어댑터가 먼저 필요하다.
  심각도만 계산한 단순 방법을 TORAI 재현이라고 부르면 안 된다.

## 4. EviRCA — 근거 수집과 판단을 분리해도 원인 선택은 어렵다

**논문:** *EviRCA: Decoupling Evidence Extraction from Reasoning for Microservice
Root-Cause Analysis* — arXiv 2609.19825v1, 2026-09-17 프리프린트.
원고에는 제목·저자 목록이 provisional이라고 표시된다.
[논문](https://arxiv.org/html/2609.19825v1) ·
[저자 연결 코드](https://github.com/yuhao541/EviRCA)

- **주제·배경:** LLM 에이전트가 거대한 관측자료를 읽고 분석 코드를 만들며 원인을 찾는다.
- **발견한 문제:** 탐색·이상 탐지·원인 추론을 하나의 루프에 맡기면 비용이 크고,
  잘못된 필드나 근거를 생성하며 진단이 불안정해진다.
- **왜 중요한가:** 비용·시간이 많이 드는데도 실제 원인을 안정적으로 찾지 못하면
  운영에 적용할 이유가 약하다.
- **해결 방법:** 결정적 추출기로 메트릭·로그·트레이스를 근거 카드로 만든다.
  LLM은 정해진 읽기 전용 도구로 카드, 호출 관계, 지표와 로그 근거를 조회하고 판단한다.
  배포 정보에 따라 pod/서비스/노드 근거도 통합한다.
- **결과·결론:** OpenRCA 335건에서 모든 요청 필드를 맞히는 Correct 40.6–43.9%와
  비용 감소를 보고했다. RCAEval의 원인 서비스 Top-1과는 다른 점수다.
  단일 장애 **실패 사례 중** 약 35%가 더 강한 피해 신호를 원인으로 선택한 경우였다.
  전체 사고의 35%라는 뜻이 아니다.
- **우리 연구에 주는 의미:** 근거가 있어도 판단은 실패할 수 있다는 문제 근거다.
  그러나 이미 호출 방향을 추론하고 관계 수를 제한하므로 ‘기존에는 방향/선별이 없다’고
  차별성을 주장하면 안 된다. 공개 구현은 호출 빈도로 그래프 표시를 최대 40개 연결로 줄인다.
- **baseline 가능 여부:** 가장 가까운 LLM 비교 대상으로 적합하다. 현재 어댑터는
  OpenRCA Bank/Telecom/Market 대상이며 RE2에 바로 적용되는 것이 아니다.
  하루 전체 통계 대신 어떤 정상 기간을 허용할지 등 동일 조건의 어댑터를 먼저 검증해야 한다.

## 5. TopoEvo — 학습 기반 후보 부분 그래프도 이미 존재한다

**논문:** *TopoEvo: A Topology-Aware Self-Evolving Multi-Agent Framework for Root Cause
Analysis in Microservices* — arXiv 2605.15611v1, 2026-05-15 프리프린트.
[논문](https://arxiv.org/html/2605.15611v1)

- **주제·배경:** 연쇄 증상, 서로 다른 관측자료, 변하는 토폴로지 때문에 큰 이상을
  보이는 서비스를 원인으로 오인할 수 있다.
- **발견한 문제:** 학습된 그래프 표현을 LLM이 검증 가능한 근거로 사용하기 어렵고,
  관계없는 영역까지 추론하면 잡음이 늘어난다.
- **해결 방법:** 다중 관측 표현과 GAT 기반 위치 추정, 증상 토큰을 결합한다.
  상위 후보의 H-hop 부분 그래프로 범위를 제한하고 가설–근거–검증 에이전트를 사용한다.
- **결과·결론:** 공개 환경과 운영 플랫폼에서 개선을 보고했지만 모든 지표에서
  최상위는 아니었다. 여러 모듈·기억·적응이 함께 바뀌므로 선별 단독 효과와 구별해야 한다.
  본문 일부 숫자와 표의 숫자에도 불일치가 있어 주장 강도를 낮춰 읽어야 한다.
- **우리 연구에 주는 의미:** “학습으로 후보를 고르고 그래프 범위를 줄인다”도
  차별성으로 충분하지 않다. **같은 비용에서 규칙보다 유용한 연결을 고르는지**가 필요하다.
- **baseline 가능 여부:** 직접적인 방법론 비교 대상으로 중요하다. 공식 실행 코드·명확한
  재현 조건은 확인하지 못했으므로 당장 실행 가능한 주 기준점으로 약속하지 않는다.

## 6. EG-RCA — 근거 품질 개선이 진단 정확도 개선과 같지는 않다

**논문:** *Improving microservice failure diagnosis with llms and observability evidence*
— Universum: Technical Sciences, 2026, 9(150), DOI 10.32743/UniTech.2026.150.9.23417.
[출판사 원문](https://7universum.com/en/tech/archive/item/23417)

- **주제·배경:** LLM은 그럴듯하지만 근거 없는 원인이나 전파 설명을 만들 수 있다.
- **발견한 문제:** 근거가 다른 개체를 가리키거나 시간·경로가 연결되지 않아도 설명은
  자연스럽게 보인다. 설명의 설득력과 실제 진단 정확도는 다르다.
- **해결 방법:** 시간·토폴로지·이상·의미 일치 등의 규칙으로 근거를 순위화하고,
  후보별 제한된 근거를 LLM에 제공한다. 인용·경로·시간의 일관성을 점검한다.
- **결과·결론:** 주 평가의 많은 부분은 결정적 순위화 파이프라인이다.
  고정 LLM 예비 평가 12건에서 Evidence F1은 개선됐지만 **위치 진단은 두 조건 모두 75%**였다.
  모든 검증 모듈의 효과를 평가한 것도 아니다.
- **우리 연구에 주는 의미:** 관련 근거를 잘 고르는 것과 원인을 더 잘 찾는 것을
  별도로 채점해야 한다. 정답 연결이 없는 RCAEval에서는 근거 F1을 꾸며낼 수 없다.
- **baseline 가능 여부:** 시간·관계 기반 규칙을 설계할 참고 자료다.
  공개 실행 artifact는 확인하지 못했다. 작은 LLM 실험과 출처 특성을 고려해
  이 논문 하나를 핵심 타당성 근거로 삼지 않는다.

## 7. 데이터 근거: RCAEval은 무엇을 검증할 수 있는가?

**논문:** *RCAEval: A Benchmark for Root Cause Analysis of Microservice Systems with
Telemetry Data* — WWW Companion 2025, 4쪽.
[논문](https://arxiv.org/html/2412.17015v4) ·
[공식 저장소](https://github.com/phamquiluan/RCAEval)

서로 다른 비공개 데이터와 평가 방식 때문에 RCA 결과 비교가 어려운 문제를 해결하려고,
실행 중인 벤치마크 시스템에 주입한 장애의 관측자료·원인 정답·평가 환경을 공개했다.
실제 시스템에서 수집한 자료지만 자연 발생 운영 장애 735건이라고 소개하면 안 된다.
현재 확보한 RE2-OB/TT 180건은 원인 서비스 순위 평가에 적합하며 인과 연결 정답은 없다.

추가 코드 점검에서 RCAEval harness가 정답 서비스로부터 SLI 이름을 만드는 경로를 확인했다.
BARO/TORAI의 확인한 함수는 해당 인자를 사용하지 않지만, 새로운 SLI 기반 어댑터가 그대로
가져가면 정답 누출이 될 수 있다. **호출 인자까지 확인해야 공정한 baseline이다.**

## 8. 조사에 따른 연구 방향

| 주장 | 판단 |
|---|---|
| 기존 연구는 원인과 피해를 구분하지 않았다 | 틀림. 여러 연구의 핵심 과제다 |
| 기존 연구는 호출 방향을 쓰지 않았다 | 틀림 |
| 관련 없는 연결을 줄이면 새 연구다 | 불충분. MicroHECL·EviRCA·TopoEvo·EG-RCA와 겹친다 |
| 근거 선별 점수가 좋아지면 RCA도 좋아진다 | 보장되지 않음. 최종 진단을 직접 비교해야 한다 |
| 학습 선별이 동일 비용의 규칙·후보 부분 그래프보다 유리하다 | 검증할 가치가 있는 가설. 아직 입증되지 않음 |
| LLM을 넣어야만 좋은 RCA가 된다 | 근거 없음. 수치 기반 방법과 반드시 비교해야 한다 |

따라서 본 연구는 **‘새 그래프를 쓰는 연구’가 아니라, 제한된 관측자료에서 어떤 근거가
진단에 실제로 기여하는지 통제해 검증하고, 필요한 경우에만 학습 선별을 개발하는 연구’**로
설계한다. 연구의 출발점은 유효하지만 독창적인 방법과 성능 향상은 아직 확보된 결과가 아니다.

## 조사 범위와 남은 확인

위 6편과 RCAEval의 원문 및 가능한 저자 코드를 중심으로 조사했다.
모든 관련 논문을 망라했거나 전 세계 최초성을 검증한 조사는 아니다.
논문 원문과 코드의 차이, 공개 구현 부재, 데이터 어댑터 필요성을 확인했으며,
**이번 작업에서 BARO·TORAI·EviRCA 전체를 실행·재현하지는 않았다.**
