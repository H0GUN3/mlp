# 데이터 활용 적합성 확인 실험

## 목적과 현재 승인 범위

사용자는 데이터별 적합성 재평가에서 확인할 부분을 정리하고 실험으로 확인해 보고하라고 요청했다.
이번 목적은 최종 모델의 성능 입증이 아니라 **각 데이터에 맡긴 역할이 실제 근거로 성립하는지**
검증하는 것이다. 사전 점수나 이전 답변을 사실로 가정하지 않는다.

기존 자료·결과는 읽기 전용이며, 이 폴더에만 새 코드·결과·보고서를 작성한다.
대규모 추가 다운로드, 새 신경망 학습, 최종시험, 원본 수정, 설치, 프로젝트 commit은 하지 않는다.
원래 RCAEval 최종36건과 native test/unassigned 관측·예측에는 접근하지 않는다.
RCAEval 전체 인덱스와 배포 목록은 관측이 아닌 메타데이터로만 사용한다.
원자료를 다시 읽을 필요가 없는 검사는 저장된 감사 결과와 해시를 재사용한다.

## 최신 근거의 정정

이전 369/350이라는 수는 원래 정답 목록의 단일 항목과 최소 관측 지원 수다.
`research_reset_review_20261016`의 전체 설정 해석에서는 비network1,168건 중
충돌1건을 제외한 **1,167건을 명목상 단일 설정 표적 과제의 검토 후보**로 확인했다.
이를 물리적 인과 원인이 입증된 1,167사건 또는 승인된 최종 학습 집합이라고 하지 않는다.

`diagnostic_observability_20261016`은 HTTP796건의 관측을 읽었으나,
대부분 사례의 서비스별 상세 수치는 정답 표적/상대 서비스만 저장했다.
이를 전체 후보의 진단 점수 입력으로 재사용하면 정답을 이용한 후보 선택이 된다.
따라서 아래 HTTP 실험에 필요한 **모든 관측 서비스의 상태 집계**는 새로 계산한다.

## 확인 가설과 실제 확인 작업

### R1. RCABench에서 관측만으로 전체 후보의 순위를 계산할 수 있는가?

관측 가용성 평가는 기존 manifest의 **HTTP796사례 전수 검사**를 재사용한다.
새 진단 순위 실험은 미래 평가 후보를 전부 개발에 노출하지 않도록 다음 개발 부분집합에 한정한다.
각 HTTP종류에서 `semantic_configuration_sha256` 그룹을
SHA256(`"suitability-pilot-20261016:"+group_key`) 순으로 정렬하고 앞 ceil(그룹수×0.2)를 선택한다.
이전 정밀 표본에 포함된 HTTP사례가 속한 그룹은 모두 개발 부분집합에 추가한다.
같은 설정 그룹의 사례를 모두 포함하며 목록·선택 이유·분할 hash를 점수 계산 전에 저장한다.
이미 관측을 깊이 확인한 사례를 새 미접촉 사례로 돌리지 않기 위한 정책이다.
관측 밀도나 모델 점수를 보고 사례를 삭제하지 않으며, 기존 표적 trace 누락2건도 포함한다.
나머지 HTTP사례에는 새 순위 점수를 계산하지 않고 보류 후보로 남긴다.
이 후보도 기존 관측 감사 이력이 있으므로 완전한 미접촉 최종자료라고 인증하지 않는다.
다른626건은 최신 전체 메타데이터/품질 근거로 활용 범위를 평가하되,
HTTP 상태 기반 점수 결과를 그 사례들에 일반화하지 않는다.

1. 기존 archive를 한 번 순회하며 사전 선택된 개발 사례의 정상·장애 trace파일만 필요한 열로 읽는다.
   기존 파일별 SHA256과 크기를 대조한다. 전체 압축해제는 하지 않는다.
2. 서비스별 전체 span 행 수, 유효 HTTP상태 행 수(100–599), HTTP오류 행 수(400–599),
   span 상태 Error 행 수를 집계한다. Unknown/Unset을 HTTP정상으로 치환하지 않는다.
3. 저장된 시간 경계에 대해 정상 `[normal_start, normal_end)`,
   장애 `[abnormal_start, abnormal_end)`를 사용한다. 공통 경계는 장애 쪽에만 남긴다.
   삭제된 끝 경계 행 수와 구간 밖 행 수를 별도 기록한다.
4. 요청 수가 아니라 **배포된 span 행 기반 빈도**다. 동일 요청의 Client/Server 등
   여러 span은 그대로 세며 독립 요청/사건으로 부풀리지 않는다.
5. 후보는 기존 전체 관측 census의 정상·장애 gauge/trace 서비스명 합집합이다.
   빈 이름만 제외하고 loadgenerator 이름도 포함한다. 정답30서비스로 축소하지 않는다.
   이름을 진단 특성으로 쓰지 않고 결과의 서비스 매핑에만 사용한다.

다음 네 기준을 결과를 보기 전에 고정한다.

| 기준 | 서비스 점수 |
|---|---|
| 균등 기준 | 모든 후보 동점 |
| 장애 HTTP오류 비율 | 장애 HTTP오류 행 / 장애 유효 HTTP상태 행 |
| HTTP오류 비율 증가 | 장애 비율 − 정상 비율 |
| 장애 span Error 비율 | 장애 span Error 행 / 장애 전체 span 행 |

분모가 없거나 필요한 기간의 관측이 없으면 점수는 결측이다. 결측 후보를 삭제하거나
0점 정상으로 처리하지 않고, 지원되는 모든 점수 뒤에 동점으로 배치한다.
전 후보 결측이면 전체 동점이다. 점수 함수에는 정답·주입 종류·사례명을 전달하지 않는다.

평가는 두 정답 계약을 **동일 점수에서 별도** 비교한다.
- 설정의 애플리케이션 표적 하나: 명목 설정 표적을 찾는 과제.
- 배포본의 원래 정답 서비스 집합: 적어도 하나의 허용 정답을 찾는 과제.

두 계약의 Top1/Top3/MRR 차이는 방법의 개선이 아니라 **평가 질문 변화**다.
동점 순서는 균등 무작위 순위의 기대값으로 처리한다. 복수 정답은 첫 허용 정답의
순위에 대한 기대 reciprocal rank와 Top-k 포함 확률을 사용한다.
정답이 후보에 없다면 별도 보고하고 해당 사례 점수는0; 후보를 정답으로 확장하지 않는다.
선택된 개발 사례의 사례 균등 평균·고장 종류별 결과·결측 후보/표적 수를 모두 보존한다.
20% 그룹 표본과 이전 정밀 표본 추가로 구성된 개발 결과를 HTTP796건 전체 성능으로 부르지 않는다.
실제 HTTP오류가 큰 서비스가 설정 표적이라는 가설을 지지하는지와 반례를 함께 보고한다.

**이것은 BARO/Eadro/DiagMLP 재현이나 새 모델 제안이 아니다.**
장애 시점과 전체 관측 구간이 주어진 오프라인 자료 진단 실험이다.
단순 기준 성능이 낮다는 이유만으로 데이터가 부적합하다고 판정하지 않는다.

### R2. RCABench의 반복 설정을 구분한 분할이 가능한가?

전체1,422건에서 기존 `semantic_configuration_sha256`을 그룹 키로 쓴다.
SHA256(`"suitability-20261016:"+group_key`)을 정수화한 나머지3으로 임시 fold를 만든다.
비교용으로 case ID 해시 나머지3도 계산해 반복 설정이 여러 fold로 나뉘는 규모를 보고한다.
설정 그룹은 실제 독립 수집 사건의 인증이 아니다.
두 후보 분할의 root/유형 지원, namespace/시간 공유를 메타데이터로 분석한다.
공식 최종 분할로 채택하거나 모델을 학습하지 않는다.

### E1. Eadro는 개발에 적합하지만 독립 평가에는 무엇이 제한되는가?

기존 허용 개발 bundle과 전체 메타데이터 감사만 사용한다.
새 모델을 학습하지 않고 다음 임시 분할의 TRAIN root·유형 지원과 정상 창 지원을 비교한다.
- 기존 사건3-fold: 서비스는 알려져 있고 다른 장애 사건을 평가.
- recording holdout: 수집 환경뿐 아니라 세 원인 서비스의 정답 학습 사례도 빠지는지.
- 고장 종류 holdout: 원인 서비스는 유지하면서 새로운 고장 종류가 되는지.

SN36/TT81이라는 숫자만으로 학습 불가능 또는 부적합이라고 판정하지 않는다.
정상 archive를 추가로 풀어도 장애 정답 사례가 증가하지 않는다는 기존 해시 검증은 재사용한다.
이미 사용한 개발 사건을 새로운 미접촉 최종평가로 부르지 않는다.
기존 모델 실험과 정보 손실 검증은 재실행하지 않는다.

### A1. RCAEval의 관련 전체 자료를 확보하면 어떤 평가가 가능한가?

전체735행 사례 인덱스, 고정 배포 파일 목록, 기존 감사만 사용한다.
SockShop과RE1은 현재 trace필수 주실험에서 제외한다.
RE2-OB/TT180건의 반복 그룹과 RE3-OB/TT60건의 원인·유형 분포를 비교한다.
RE2 반복 그룹을 통째로 holdout할 때의 원인·유형 지원과
RE2→RE3로 평가할 때의 원인 서비스 중복/새 고장 조건을 실제 집계한다.
RE3 60건을 새로 다운로드하거나 원관측을 열지 않는다.
관련 전체240건은 확보 가능 규모이지 자동으로 쓸 수 있는 최종시험 사건 수가 아니다.
기존 개발/최종 역할 잠금과 메타데이터 범위만 확인하고 분할 파일을 수정하지 않는다.

### O1. ops-lite 30건은 전체455건을 대표하며 RCABench와 독립적인가?

455건의 기존 label/injection/env/causal_graph metadata 및
30건 관측에 대한 기존 파일 해시·감사 결과만 사용한다.
전체와 현재 선택 표본의 시스템, 원인 항목 수, 장애 종류 분포를 비교해 선택 편향을 정량화한다.
표본 밖425건의 관측 품질을 표본30건으로 보증하지 않는다.
RCABench와 사례명·주입 식별자·시간/설정 및 확보 관측 파일의 비어 있지 않은 바이트 해시를
대조한다. 일치0건은 독립성 증명이 아니고, 재포맷·시간 이동 중복까지 부정하지 않는다.
서로 다른 정답 계약은 보존하고 외부 배포의 공식성도 확인된 사실과 미확인을 구분한다.
새 관측 다운로드는 하지 않는다.

## 계산 환경과 보존

- JSON/메타데이터는 표준 라이브러리, 수치 계산은 NumPy.
- 실제 Parquet는 기존 `.venv-mlp` Python3.10/NumPy1.26.4/PyArrow19.0.1 사용.
  시스템 Python의 Arrow 호환 문제를 피하며 새 설치·전역 변경은 하지 않는다.
- 실제 archive 순회는 단일 프로세스, Arrow 계산/I/O 각2스레드 이하.
- 원본을 수정하지 않고 결과 JSON은 exclusive-create한다.
- 입력/코드 SHA256, 읽은 파일/행 수, 실행 시간·최대 RSS와 명령 exit를 기록한다.
- 실행 증거는 보고서의 주장뿐 아니라 원래 monitor 완료 알림·bash 상태의 정확한 인용과
  session/monitor 식별자를 함께 보존한다. 검증자가 그 기록을 읽을 수 있게 한다.

## DAG 실행 계획

한 실험·판정 phase의 모든 알려진 단계를 한 run에 정의한다.

| 노드 | 범위와 산출물 | 분류 |
|---|---|---|
| rcab | rcab_trial.py/test_rcab_trial.py, rcab_trial.json, RCAB.md | deep-low: 전체 후보 집계·두 정답 계약·동점·결측·분할을 연결 |
| rcaeval | rcaeval_trial.py/test_rcaeval_trial.py, rcaeval_trial.json, RCAEVAL.md | quick: 정해진 메타데이터 분할·지원 집계 |
| eadro | eadro_trial.py/test_eadro_trial.py, eadro_trial.json, EADRO.md | quick: 기존 분할 함수/메타데이터의 지원 비교 |
| ops | ops_trial.py/test_ops_trial.py, ops_trial.json, OPS.md | unspecified-low: 서로 다른 metadata 계약의 중복과 표본 편향 판정 |
| verify | 네 producer를 모두 읽고 VERIFY.md 작성 | unspecified-low: 실제 검사·수치·보호 경계·실행 증거 대조 |
| report | VERIFY.md와 네 보고서를 읽어 REPORT.md 작성 | writing: 처음 읽는 사람용 한국어 종합 |
| report-check | REPORT.md와 JSON을 대조해 REPORT_CHECK.md 작성 | quick: 수치·링크·요구사항 대조 |

첫 wave 폭4, 이후 verify→report→report-check.
각 노드는 자기 파일만 쓰고 downstream은 지정된 인계 파일을 읽는다.
주 담당은 완료된 결과를 직접 확인하고 최종 판정한다.

## RESULT VERIFICATION과 종료 기준

완료 알림은 검증 전까지 성공의 근거로 취급하지 않는다.
집중 테스트와 명시적 Pyright exit0, 실제 분석 exit0 및 원래 실행 기록,
전체 후보 생성의 정답 비의존성, 두 계약의 동점 채점, 경계/결측 처리,
그룹 분할 비중첩과 지원 수, 표본 분포/중복 집계, 입력/기존 결과 hash 보존을 확인한다.
같은 검사라도 입력·코드가 바뀌거나 실패한 경우에만 재검사한다.

최종 보고서는 데이터별로 **통과한 활용 조건 / 반증된 주장 / 아직 미확인 / 권장 역할**을
구분한다. 모델 성능 실험이 없는 자료를 학습 검증 완료로 표현하지 않는다.
전체 수집이나 주 데이터 최종 채택을 자동 실행하지 않고 결과 보고에서 종료한다.
