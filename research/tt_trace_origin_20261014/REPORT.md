# TT 지연 관측 부재: 한 기록·세 사건의 단계별 추적

## 먼저 결론

**선정한 food 서비스 두 장애의 지연값은 가공 중 사라진 것이 아니라,
공개 원 트레이스부터 없었다.** 주입 기록과 정답 창의 대응 오류도 없었다.

그중 손실 장애에는 원인 서비스의 DB 연결 실패 로그가 1건 존재하지만,
현재 모델 입력은 로그를 포함하지 않는다. 그 로그가 있는 창에서 저장된
세 모델 모두 원인 서비스를 1위로 고르지 못했다.

이는 **주입 정답이 있는 사건이라도 현재 선택한 관측 자료에는 직접 단서가 부족할 수
있고, 다른 자료에 있는 단서는 입력에서 빠져 있는 구체적 사례**다.
전체 데이터 오류, 로그 추가 효과, trace 수집 실패의 인과 원인을 확정한 결과는 아니다.

## 범위

- 기록 하나: `TT.2022-04-17T212101D2022-04-17T230842`.
- 정합성 대조: 해당 기록의 장애 metadata 9건 및 허용 개발 창 460개.
- 원자료 관측: food 지연(fault01), food 손실(fault02), travel 지연(fault04)의
  허용 개발 창 134개. 파일명/metadata 순서로 고정했으며 예측 점수로 고르지 않았다.
- 보호 평가 창, 다른 기록/시스템, 새 모델·재학습은 조사하지 않았다.

## 1단계 — 장애 대상·시각·정답이 잘못 연결됐는가?

원 주입 metadata의 컨테이너 이름을 서비스 이름에 대응시키고,
기존 record +16h 좌표 변환과 10초 창 규칙을 독립 대조했다.

- 서비스 이름·root 인덱스·고장 종류·시각: 9건 모두 현재 manifest와 일치.
- 허용 개발 창의 정답·event ID: 460개 모두 일치.
- 정수 반올림 구간과 원 소수점 구간의 overlap 정답 차이: 0개.
- 기록 시작·종료는 변환 후 파일명 시각과 일치.

**판정:** 이 기록의 정답 연결/창 경계 오류는 발견하지 못했다.
주입 metadata와 일치한다는 뜻이며, 실제 fault 활성화나 물리 시계 동기화를
독립 장비로 검증했다는 뜻은 아니다.

## 2단계 — 원 트레이스가 가공 중 삭제됐는가?

같은 원 spans.json에서 선택한 개발 창의 모든 후보 서비스를 재집계했다.
36,180개 서비스×초 위치에서 span 수·평균 지연·observed mask가
현재 저장 입력과 각각 정확히 일치했다.

| 사건 | 개발 창 | 원인 서비스 trace가 있는 창 | 원인 span 수(중복 포함) | root 고유 span | 원인 서비스 로그 |
|---|---:|---:|---:|---:|---:|
| food 지연 | 46 | 0 | 0 | 0 | 0 |
| food 손실 | 43 | 0 | 0 | 0 | 1 |
| travel 지연 | 45 | 19 | 145 | 29 | 102 |

food 지연 44개·손실 41개 창은 전체 10초가 주입 구간 안에 있는데도
root trace가 없다. 따라서 주입 경계에 걸친 일부 창만의 문제는 아니다.

같은 food 두 사건의 창들에는 다른 서비스 span이 각각 1,225/1,400개,
로그가 714/817개 있다. 파일 전체가 비어 있거나 모든 수집이 멈춘 상황은 아니다.
다만 span이 있는 창은 각각 7/8개이고 반복 수집된 span도 있으므로,
그 총수를 지속적 요청량이나 완전한 관측의 증거로 해석하지 않는다.
선택한 span에서 food endpoint에 해당하는 이름/URL 단서도 찾지 못했다.

**판정:** food의 root trace 관측 부재는 현재 전처리 이전, 공개 원자료에서 이미 존재한다.
서비스별 무요청·sampling·계측/수집 누락 중 어느 것인지는 아직 구분되지 않는다.
다른 서비스가 관측됐다는 사실만으로 food 서비스 수집이 정상이라고 보증할 수 없다.

## 3단계 — 원 트레이스가 없으면 장애 단서 자체도 없었는가?

food 손실의 허용 개발 창 `original_index=183`에서 다음 로그 1건을 확인했다.

```text
2022-04-17 13:51:40.108 ... org.mongodb.driver.cluster :
Exception in monitor thread while connecting to server ts-food-mongo:27017
```

기존 log +8h 좌표에서 시각은 `1650232300`이며,
주입 구간 `1650231903.018547`부터 `1650232503.018547` 안이다.
로그 소유 서비스는 `ts-food-service`다. timestamp를 해석하지 못해 누락된
로그 줄은 이번 원파일 검사에서 없었다.

이것은 DB monitor 연결 실패를 기록한 **장애 관련 단서**다.
사용자 요청 처리 로그는 아니고, 해당 주입이 이 오류를 일으켰다는 독립 인과 증거도 아니다.

현재 18개 입력 특징은 메트릭 7개와 latency·span count의 두 통계씩이며 로그가 없다.
따라서 이 로그의 내용은 현재 입력에 직접 들어가지 않는다.
동일 창의 고정 Directed validation 예측을 원 index·event·root와 hash 대조했다.

| 학습 seed | 실제 원인 food의 순위 | 1위 예측 |
|---|---:|---|
| 11 | 4위 | ts-travel-service |
| 23 | 6위 | ts-verification-code-service |
| 37 | 4위 | ts-food-map-service |

순위에 동점은 없다. 하나의 창을 세 모델로 평가한 것이지 독립 장애 3건은 아니다.

**판정:** 이 한 창에서는 모델이 보지 못한 장애 관련 단서가 원 로그에 있고,
모델은 원인 1위 식별에 실패했다.
하지만 “그 단서를 넣으면 맞힌다”거나 “로그 제외가 실패의 유일한 원인”이라는
가정은 실험하지 않았다. 다른 메트릭만으로 해결 가능했는지도 분리하지 못했다.

## 여기서 멈추는 이유와 좁은 다음 질문

이번에 가장 앞까지 확인한 문제 지점은 **원자료의 root trace 부재와
현재 입력의 로그 단서 미포함**이다. 원인이 있는 데이터 경로를 확인했으므로
모델 규모/학습량으로 바로 설명하지 않는다.

trace가 왜 없었는지를 더 구분하려면 이 recording의 실제 workload 요청 기록과
trace 계측·sampling·수집 설정이 필요하다. 선택한 관측 파일만으로
“아예 호출하지 않았다” 또는 “수집기가 놓쳤다”를 결정할 수 없다.
범위를 지키기 위해 다른 recording이나 새 데이터 수집으로 확장하지 않았다.

후속 연구 판단의 좁은 질문은 **“현재 입력에 없는 로그 단서가 네트워크 오답에서
반복적으로 나타나며 정량적 개선으로 이어지는가?”**다. 이는 검증 후보일 뿐
새 방법론 채택이나 추가 실험 승인이 아니다. 단일 사례만으로 로그 모델을 만들지 않는다.
