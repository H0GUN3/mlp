# 원인 진단에 필요한 관측과 연구 범위

2026-10-16. 자료 감사·문헌 대조 결과다. **교정 분할의 새 학습·평가는 아직 실행하지 않았다.**
첫 평가 자료 선택 질문이 열려 있다. 이를 성능 평가 완료로 표시하지 않는다.

## 1. 핵심 결론

1. RCABench의 일부 실제 사례에는 **같은 요청에서 backend는200, frontend는500을
   기록한 구분 단서**가 있다. 단순히 “필드가 있다”를 넘어 실제 값을 연결해 확인했다.
2. 반대로 주입 표적 trace는 없어지고 상대 서비스의 오류만 다수 남는 사례도 있다.
   따라서 가장 느리거나 오류가 많은 서비스를 고르는 규칙은 원인 판정과 같지 않다.
3. 현재18개 특징은 실제 SN394개·TT4,069개 개발 창에서도 시간 순서와
   채널 간 시간 정렬을 없앤다. 그러나 이 손실이 기존 모델의 오진 원인인지는 별도다.
4. Eadro 계열은 시간·로그 encoder를 이미 갖는다. 지금은 이를 버린 자체18특징이나
   전체 평균 상대값을 연구의 핵심으로 고집할 근거가 부족하다.
5. DiagMLP가 전역 문맥을 못 본다는 주장은 틀리다. 확인된 입력 누락과
   특정 사건의 오분류를 연결한 뒤 최소 변경을 정해야 한다.
6. 당장 교정 평가를 시작할 자료로는 원형 앞단을 유지할 수 있는 **SN**을 권한다.
   이는36사건의 개발 재분석이지 최종 일반화 증명이 아니다.
   RCABench HTTP는 관측이 풍부한 확장 후보이나 입력 adapter·정답 의미를 정해야 한다.
   원형 Eadro TT와 RCABench의 TrainTicket 자료는 같은 corpus가 아니다.

## 3. 실제 원인 후보를 구별하는 단서

### 3.1 frontend 오류와 backend 응답을 같은 요청에서 연결

사례: `ts2-ts-ui-dashboard-response-replace-code-qzfj27`.
설정 표적은`ts-ui-dashboard`, 상대는`ts-consign-service`.
정답 목록은 두 서비스지만, 이번 분석에서는 원래 주입 설정도 별도로 대조했다.

같은 trace 안에서 parent/span ID를 연결한 결과:

| 기간 | UI측 상태 | consign측 상태 | 연결 수 |
|---|---:|---:|---:|
| 정상 | 200 | 200 | 111 |
| 장애 | 500 | 200 | 810 |
| 장애 | 200 | 200 | 13 |
| 장애 | HTTP상태 미기록 | 200 | 16 |

이810개는 **810번의 독립 장애가 아니라 한 사건 안의 연결된 span 쌍**이다.
UI와 consign 양쪽 모두 Server kind여서 Client→Server만 인정하면 연결을 놓친다.
parent 연결은 직접 wire exchange의 보증이 아니므로 “요청 계보의 연결”이라고 부른다.

여기서는 **backend의 HTTP200 이후 UI측 HTTP500이 기록되는 경계**를 관측할 수 있다.
주입 설정과도 일치하는 단서다. 다만 HTTP200이 응답 본문의 업무적 정합성까지
증명하거나, 이 패턴만으로 모든 운영 장애의 인과 원인을 확정한다는 뜻은 아니다.

이 정보는 서비스별 평균 지연만 남기는 Eadro 공개 포크의 trace 입력이나
우리18특징에는 직접 들어 있지 않다. 단, 로그·지연 등 다른 입력을 통해
동일 사례를 이미 맞힐 가능성은 있으므로 **누락 자체를 오진 원인으로 단정하지 않는다.**

### 3.2 오류가 가장 많은 서비스와 주입 표적이 다를 수 있음

사례: `ts2-ts-basic-service-request-replace-method-v6gzn8`.
설정 표적은`ts-basic-service`, 상대는`ts-station-service`.

- 정상에는 basic→station의 Client/Server 연결1,635개가 있고 모두HTTP200/200.
- 장애에는 basic의 유효 trace 행이 없다.
- station의 Server span10,445개 중HTTP4xx/5xx는10,428개.
- 이 station Server span들은 span status가모두`Unset`이다.
- basic에는 장애 구간 로그31,405행이 남아 있다. 따라서 trace 부재=관측 전체 부재가 아니다.

이 사례는 “station의 오류가 많으니 station이 유일 원인”이라고 판단하면 위험함을 보여준다.
`Unset`을 정상으로 해석해도 오류를 놓친다. 반면 basic 로그의 구체적인 오류 의미까지
검증한 것은 아니므로 로그 존재만으로 식별 완료라고 하지 않는다.

### 3.3 전체 HTTP에서의 관측 범위

| 설정 표적 서비스에서 확인 | 사례 수/796 |
|---|---:|
| 정상 trace 행 존재 | 796 |
| 장애 trace 행 존재 | 794 |
| 장애 구간 유효 HTTP상태 존재 | 794 |
| 장애 구간 하나 이상의HTTP4xx/5xx | 750 |
| 장애 구간 하나 이상의span status Error | 699 |

전체 서비스의 HTTP상태를 가진 span은 정상35,972,449행, 장애21,452,969행이다.
HTTP오류는 각각3,599행/1,396,709행이다. 이들은 span 행 수이며 독립 요청·사건 수가 아니다.
오류 존재가 원인 판정은 아니며, 표적의 모든 행이 해당 주입 API라는 뜻도 아니다.

### 3.4 로그의 단순 키워드는 정답이 아님

UI 예시의 정상 로그6,715행은 전부 `error/exception/...` 정규식에 걸렸지만,
ERROR/FATAL/CRITICAL level은0행이고 UI의 정상HTTP오류도0건이었다.
따라서 문자열`error`를 포함한다는 이유만으로 장애 로그라고 정의할 수 없다.
14개 표본에서 사용한 제한적 주입-marker 정규식은0행이었지만,
이것으로 전체 corpus에 정답 노출이 없다고 인증하지 않는다.

## 4. 서비스마다 관측 항목이 다른가?

**공통 계측과 서비스/런타임 전용 계측이 섞여 있다.**

- SN/TT 개발 bundle에는 모든 후보에 같은7개 metric+지연+span수 슬롯이 있다.
  그러나 실제 관측률은 같지 않다. TT의27서비스 중14서비스는 허용 개발 구간 전체에서
  trace 지연이 없다. 이들은 정답으로42사건/1,779장애 창에 등장한다.
- RCABench에서는 container/pod CPU·메모리 등 공통 항목에 JVM 전용 값,
  deployment/statefulset 상태, HTTP 지연 percentile 등이 추가된다.
- 이번 읽은 자료의 metric 이름 합집합 예: mysql24종, UI30종, consign34종.
  UI/mysql에 JVM 지표가 없는 것을0으로 채워 “정상JVM”으로 해석하면 안 된다.
- API operation도 frontend는구체ID, backend는`{id}` 템플릿으로 기록되기도 한다.
  문자열이 다르다는 이유로 별개 호출로 보거나 ID를 특징으로 외우지 않도록 정규화가 필요하다.

관측 후보 이름의 합집합은50개이며 각 HTTP사례에서는49개(793건) 또는50개(3건)가 보인다.
여기에는`loadgenerator`와`loadgenerator-service`도 포함된다.
정답에 등장한30개 서비스만 남기는 방식으로 후보를 줄이면 안 된다.
실제 후보 정책은 workload generator의 역할/alias 매핑을 확인해 공통으로 고정해야 한다.

## 5. 필수 관측과 기존 앞단

모든 고장에 동일한 “필수9채널”이 있는 것은 아니다.
HTTP 실패 위치 구분에는 요청 식별·operation·상태·관계가 직접적이고,
자원 고갈에는 자원 시계열, 요청 소실에는 요청 수/관측 누락이 중요할 수 있다.
정답은 이러한 단서를 검사하는 데 사용할 수 있지만 진단 입력으로 넣지는 않는다.

현재 자체 특징은 변화 크기와 초과 비율을 남기고 시간 순서를 없앤다.
실제 모든 허용 개발 창에서 역순·공통 순열·채널별 순열을 줘도
18특징, mask, coverage가 동일했다(허용오차1e-6 아래).
이는 표현 손실의 증거이고 성능 손실이나 Transformer 우위의 증거는 아니다.

**판단:** 자체18특징을 새로운 주 앞단으로 계속 밀지 않는다.
Eadro 계열의 시계열·로그 encoder를 보존하는 것을 출발점으로 삼는다.
다만 “기존 구조”도 완전하지 않다:

- 공개 포크 trace 입력은 서비스별 초당 평균 지연이며 둘째 채널은0.
- 부모 호출쌍, operation별 상태, 요청별 분포는 그 텐서에 없다.
- 로그는 Drain 템플릿과 Hawkes baseline으로 바뀌며 문장 의미·원 변수값 그대로가 아니다.
- 논문Q/K/V attention과 확인한 포크의tanh 풀링도 구분해야 한다.

따라서 보완 후보는 “모든 특징을 새로 설계”가 아니라,
**확인된 실패에 필요한 관측 하나를 기존 앞단에서 보존하는 변경**이다.
요청 수·오류 상태·호출쌍 중 무엇이 필요한지는 교정 평가의 실제 오류에 연결해 정한다.
이런 신호는 TVDiag·DeepHunt도 사용하므로 단순 추가 자체를 신규성으로 주장하지 않는다.

## 6. DiagMLP와 상대 공유 방식에 대한 판단

사용자의 지적은 원 단위·수준이 다른 서비스 수치를 직접 평균내는 경우 타당하다.
기존 자체 구현은 서비스별 정상 기준으로 변환한 특징을 평균내므로
단순한 원 CPU/지연값 평균은 아니다. 그렇다고 정상화가 서비스 역할 차이를 없애지는 않는다.

상대항은 local-only 입력보다 문맥을 추가할 수 있지만,
DiagMLP는 이미 모든 노드 임베딩을 전역 concat한다.
전체 평균 차감만으로 원인과 전파 증상을 구별한다는 보장은 없다.
선형 공유 점수에서는 완전 관측 조건의 공통 평균항이 순위에서 소거된다.
비선형 점수에서 문맥효과가 가능하다는 사실만으로 진단 기여가 입증되지는 않는다.

**결론:** “전파 증상을 제거하는 상대 공유 방식” 주장은 버린다.
상대 공유 방식 자체를 수학적으로 무의미하다고 일반화하지는 않지만,
현재 연구의 주 제안으로 유지할 근거는 부족하다.
DiagMLP에서 실제로 확인한 것은 앞단이 넘겨주지 않은 구분자는 fusion이 직접 사용할 수
없다는 정보 경계다. 전역 concat의 용량/압축이 실제 오류의 원인인지는 미확인이다.

## 7. 선행연구는 데이터를 어떻게 사용했는가?

| 방법 | 실제 사용하는 정보/그래프 | 학습·평가에서 주의할 점 |
|---|---|---|
| Eadro | metric시간열, 로그템플릿/Hawkes, 지연시간열, 서비스 의존 그래프 | 논문은시기별60/40, 포크는창 shuffle70/30. 정확한 사건 분리는 같은 사실이 아님 |
| DiagMLP | 앞단 모달 표현+노드위치, 전역 concat fusion | validation·창누출 수정 보고. 정확한 사건 manifest는 미확인 |
| TVDiag | metric명/방향, caller/operation/상태/지연 alert, logKey; instance 호출그래프 | root-instance와고장종류 공동지도학습. 그래프 간선은 양방향화 |
| DeepHunt | 서비스+host 노드, 지연·요청수·상태·로그빈도·metrics, 호출/배치 관계 | 정상노드특징재구성 후 오류·상하류패턴 점수화. 운영자피드백으로 보완 |

선행연구도 일반적으로 새 입력의 진단을 목표로 하지만,
논문 목표만으로 해당 공개 분할의 사건 독립성을 보증할 수 없다.
반대로 명세가 부족하다고 저자들이 이미 아는 사건을 일부러 평가했다고 단정하지 않는다.
우리 교정 평가는 사건/episode를 먼저 나누고 정상 참고 구간도 함께 이동시킨다.

DeepHunt가 장애 탐지를 제외한 명시적 이유는 기존 탐지 방법을 사용할 수 있다는 것이다.
원인 진단을 못해서 제외한 것이 아니다. 시작·종료 시각 탐지 연구도 아니다.

```text
TVDiag:
관측 → 모달별 alert → instance 호출그래프 → GraphSAGE
                                    ├→ 노드별 MLP → 원인 순위
                                    └→ 그래프 표현 → 고장 종류

DeepHunt:
정상 관측·의존관계 → 그래프 autoencoder 학습
장애 관측         → 재구성 오차 → 시간·상하류 패턴 → 원인 순위
                                                   ↑ 운영자 피드백

GraphRAG 원논문:
문서 → entity·관계 → 커뮤니티 요약
질의 + 검색된 요약 → 생성·통합 답변
```

GraphRAG와 그래프 신경망은 같은 용도가 아니다.
현재49~50개 관측 이름을 직접 평가할 수 있고 별도 사건 지식 corpus도 확립되지 않았다.
GraphRAG+reranking+MLP를 추가할 필요는 확인되지 않았다.
후보를 검색결과로 제한하면 정답을 검색에서 놓친 경우 reranker는 복구할 수 없다.
따라서 이번 범위에서는 이 조합을 채택하지 않는 것이 합리적이다.

| 탐지F1 | 정상/장애의precision과recall 조화평균 | Eadro·DiagMLP |
| 종류분류F1 | CPU/메모리/HTTP등종류분류 | TVDiag. 원문의macro/micro/weighted방식미명세 |
| MRR | 정답순위의역수평균 | TVDiag는MRR@3; cutoff밖0. 일반MRR과구분 |
| 집합회수율 | Top-k가복수정답중몇개를찾았는가 | 위4편의단일원인주평가와다름. 원RCABgold-set과제에서필요시명시 |

Eadro는HR@k·NDCG, DiagMLP는Top-k, DeepHunt는A@k·Avg@5도 보고한다.
Avg@k는1~k포함정확도의평균이며MRR이아니다.
명세상 분모·gating이 불명확한 논문 숫자에 우리 정의를 대신 적용하지 않는다.
우리 단일서비스 과제의 주지표는**사건 균등Top-1**,
보조는 필요한 경우Top-3과짝지은차이/불확실성이다.
종류를 예측하지 않으면 종류F1은 추가하지 않는다.

## 10. 데이터 선택과 연구 방향

| 자료 | 지금의 장점 | 지금의 제한 | 권고 역할 |
|---|---|---|---|
| SN | 원형입력·앞단재사용, 비교적풍부한개발trace, 사건정답확인 |36사건·root종류당1사건,분할환경공유 |첫교정평가/실패원인확인 |
| 원형TT |81사건, 동일방법의다른시스템대조 |14/27서비스개발trace없음;관계증거희소 |후속희소관측강건성대조 |
| RCABHTTP |796사례·상태/operation/요청연결·사용자영향 |새metric/graph adapter,복수gold·설정표적계약,희소종류 |주실험확장후보 |

위 감사의 관측 구간은 SN/TT의 허용10초 창과 RCAB의 사례별 정상/장애 구간으로 다르다.
관측률이나 행 수를 그대로 같은 진단시간 조건의 데이터 우열·성능 비교로 사용하지 않는다.

**지금 실행 대상 하나를 고르면 SN부터**다. 이전 점수가 높았기 때문이 아니라
사용자가 요구한 기존 앞단 보존과 교정 분할을 가장 적게 바꾸고 검증할 수 있기 때문이다.
36사건으로 광범위한 일반화를 주장하지 않으며 RCABench를 동시에 새로 가공하지 않는다.
HTTP 진단을 주제로 확정한다면 RCABench가 더 직접적이나,
기존7metric·27노드·정적graph를 그대로 옮긴 원형재현이라고 부르면 안 된다.

연구 방향은 다음으로 좁힌다.

1. 목표: 발생한 장애에서원인서비스순위. 탐지·미래예측·복구·LLM은제외.
2. 비교: 원형앞단을보존한Eadro와명시적인수식기반DiagMLP복원.
3. 평가: 미학습사건분리·학습전용통계·validation선택·사건균등집계.
4. 실패를본뒤, 요청수/오류상태/호출쌍 중**필요성이확인된한항목**만보완후보로정한다.
5. 기존입력에서도단서가보존됐다면앞단을바꾸지않고후단의실제실패를분석한다.
6. 단서가없거나기존법으로충분하면제안가설을버린다. 평균상대/Transformer를기정사실화하지않는다.
