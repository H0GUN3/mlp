# 개발용 기준점·실패 분석 사전 명세

## 사용자와 확정한 방향
- 단일 원인 서비스 진단부터 시작한다. 여러 서비스에 나타나는 증상은 함께 다룬다.
- 정확도가 주목표이며 시간·비용은 보조 지표다. 실제 복구·응답시간 회복은 범위 밖이다.
- LLM은 필수 구성요소가 아니다. 기존 방법이 실패하는 조건을 확인한 다음 필요한
  처리 역할을 정하고, 그 역할에서 추가 가치가 있을 때만 사용한다.
- 이번 단계는 기준점의 개발용 평가이며 제안 방법·최종 시험·학습 실험이 아니다.

## 데이터 경계
- `research/smoke/manifest.json`의 `reserved_development_cases` 합집합 36건만 사용한다.
- 12개 시스템/원인서비스/장애유형 그룹 × 반복 3회다. 36개의 독립 장애 조건이 아니다.
- 원래 smoke 12건을 포함한다. 나머지 144건의 관측자료는 읽거나 평가하지 않는다.
- 144건을 최종 시험으로 확정하는 것은 아니다. 추후 학습/검증/시험 분할은 별도 결정한다.
- 현재 확보한 RCAEval 고정 커밋과 이전 해시 검수 증거를 재사용한다.
- 정답은 분할 확인과 채점에만 사용한다. scorer 함수에 정답 서비스·장애 유형·
  사례명을 전달하지 않는다. 주입 시각은 공통으로 알려진 장애 시작 시각이다.

## 비교할 세 방법

### 1. 기존 중앙값 변화 기준점
- 첫 smoke의 `scripts/smoke.py::build_features`, `metric_change`와 같은 규칙을 사용한다.
- 유효한 정상/장애 값 각각 20개 이상. 중앙값 변화 / max(정상 IQR,
  정상 중앙값 절댓값×0.05, 1e-9), 절댓값, 100에서 자름, 소수 3자리.
- 서비스 점수는 해당 서비스의 최대 지표 점수다. 익명 ID가 동점 순서를 정한다.
- 원래 12건은 저장된 feature를 재사용해 원래 순위 11/12·12/12와 일치함을 확인한다.
  새 24건만 같은 feature 함수를 호출하되 고정 순서·고정 seed를 기록한다.

### 2. BARO 공식 코드 정렬 점수기 — NumPy 재구현
- 기준 릴리스: `phamquiluan/baro` 0.2.0.
- 고정 커밋: `582d4ead3d3301a34fea4e395bfa3f750fc9a40d`.
- 참조 파일: `baro/root_cause_analysis.py`, `baro/utility.py`.
- 원본을 직접 설치·실행한 결과가 아니라, 아래 명시한 점수 경로를 NumPy로
  재구현한 결과다. 전체 BARO 재현이나 BOCPD 탐지 성능이라고 부르지 않는다.
- `read_data(strip=False)`에 해당하도록 전체 구간을 유지한다. 무한값→결측,
  과거 값만으로 forward-fill, 남은 선두 결측→0, latency-50 제외,
  latency-90을 latency로 이름 변경. 미래 값으로 backward-fill하지 않는다.
- 정상/장애 구간 각각에서 상수인 지표를 제거하고 공통 지표만 사용한다.
  메모리는 MB로 바꾼다. 서비스/장애 종류 기반 지표 선택 옵션은 사용하지 않는다.
- 정상 중앙값과 IQR을 계산하고, IQR이 float64의 `10×eps`보다 작으면
  RobustScaler의 0 근처 scale 처리처럼 분모를 1로 둔다.
- **부호 있는 최대 변화** `max((abnormal - normal_median)/scale)`로 지표를 순위화한다.
  동점은 원래 열 순서를 보존하며 서비스는 첫 등장 순서로 중복 제거한다.
- 어떤 서비스의 모든 지표가 탈락하면 임의 순위를 채워 넣지 않고 후보 누락으로 기록한다.

### 3. 절대 변화 최대값 변형
- 2번과 같은 전처리·후보에서 `max(abs(...))`만 적용한다.
- BARO 논문의 절댓값 서술과 공개 코드의 부호 있는 최대값 차이를 점검하는
  **진단용 변형**이다. 별도 새로운 연구 방법이나 논문 전체 재현이 아니다.

세 방법은 모든 학습/평가 자원에 동일 접근을 하되, 각 방법의 전처리는 명시적으로 다르다.
따라서 1↔2는 점수식 하나의 효과를 분리한 ablation이 아니라 방법 묶음 비교다.
2↔3만 동일 전처리에서 부호 처리 차이를 비교한다.

## 실행·검증
- 원본 데이터·첫 smoke 응답·사전 명세를 수정하지 않는다.
- 결과 전에 코드를 고정하며, 코드 hash·참조 URL/커밋·실행 환경·사례 목록을 기록한다.
- 함수 self-check: 상승/하락, IQR 0, 결측 forward-fill, 상수열 제거, 서비스 중복
  제거, 동점 순서, 라벨을 받지 않는 scorer 경계를 확인한다.
- 독립 검증 노드가 실제 저장 결과를 재채점하고 원래 12건의 기준점 결과와 대조한다.
- Top-1/Top-3/MRR, 시스템·장애 유형별 결과, 후보 누락, paired 승/패를 보고한다.
- 실패 사례마다 원인의 점수/순위와 앞선 비원인 서비스의 특징을 기록한다.
  비원인 서비스가 실제 피해 서비스라고 인과적으로 확정하지 않는다.
- 36건 및 반복 12그룹의 탐색 결과로 통계적 유의성·일반화·신규성을 주장하지 않는다.

## 진행·중단 기준
- 기준점 구현·집계 검증이 실패하면 결과 해석을 보류한다.
- 강한 기준점이 거의 모두 맞히면 이 자료에서 복잡한 진단기를 추가할 필요는 미입증이다.
- 반복되는 실패가 관측되면 해당 현상을 구체적으로 정리하되, 원인을 확인하지 않은 채
  “원인/피해 혼동”이나 “LLM 필요”로 이름 붙이지 않는다.
- 다음 방법은 실패 분석에서 얻은 근거에 따라 별도로 설계한다. 같은 개발 사례를
  고쳐 맞힌 결과를 최종 시험 성능으로 보고하지 않는다.
