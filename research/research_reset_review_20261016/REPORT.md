# 장애 정의, 모델 비교, 데이터 재구성에 대한 18개 답변

2026-10-16. **분석과 협의 자료이며 새 모델·주 데이터·분할을 확정한 문서가 아니다.**
기존 원자료·분할·모델은 변경하지 않았다. 새 학습이나 최종시험도 하지 않았다.

## 먼저 결론

우리가 풀려는 문제는 “여러 서비스에 이상이 함께 보일 때, 어디부터 점검해야 하는가”다.
그러나 **장애를 일으킨 조작, 관측된 이상, 사용자가 경험한 실패, 채점용 정답**은
서로 다르다. 이를 구분하지 않고 높은 정확도나 모델의 한계를 설명하면 잘못된다.

이번 RCABench 실제 분석은 기존의 “단일 정답 369건만 쓸 수 있다”는 해석을 바꾼다.
1,422건 전체에 사용자 영향 판정 기록이 있고, HTTP 등은 정답 목록이 두 개라도
주입 설정의 대상 애플리케이션을 별도로 식별할 수 있다. 반면 네트워크 254건은
방향이 있는 서비스 쌍으로 구분해야 한다. 설정과 정답이 충돌하는 사례도 1건 발견했다.
자세한 전체 분포와 재현 근거는 `RCABENCH_REPORT.md`에 있다.

## 1. 구체적으로 무엇을 장애라고 하는가?

다음 네 층을 구분해야 한다.

| 층 | 의미 | 예 |
|---|---|---|
| 고장 주입(fault) | 실험에서 가한 조작 | 특정 서비스 메모리 압박, 응답 코드 변경 |
| 관측 이상(anomaly) | 정상 패턴과 달라진 기록 | 지연 증가, 오류 로그, 요청 수 감소 |
| 사용자 영향(failure) | 요청의 성공·성능 조건을 충족하지 못함 | 주문 성공률 감소, 허용 지연 초과 |
| 정답(label) | 모델 학습·채점에서 맞혀야 하는 대상 | 주입 서비스, 허용 서비스 집합, 방향 있는 쌍 |

**Eadro 논문 §V-E의 장애/정상 정답은 주입 유무에 따른 창 구분**이다.
각 창이 실제 사용자 SLO를 위반했는지 별도로 검증한 정답이라는 뜻은 아니다.[P1]
로컬 `native_data.py::window_labels` 역시 10초 창과 주입 구간이 조금이라도 겹치면
장애 창으로 표시한다. 소수부를 버려 정수화한 원자료 시각과 포함형 끝점 규칙을 사용한다.
이는 모든 10초가 실패했다거나 그 시간의 모든 서비스가 고장났다는 뜻이 아니다.

RCABench 수집 논문은 성공률 하락의 Z-test와 지연의 고정 기준(예:10초)·
과거 성능에 따른 적응 기준으로 사용자 영향이 있는 주입을 선별한다.[P5]
10초가 확보본 모든 API에 일률 적용된 기준이라고 단정하지 않는다.
실제 확보본 1,422건 모두 `conclusion.parquet`에 최소 하나의
`slo_violated=true`가 있다. 다만 저장된 판정 결과를 확인한 것이며,
각 사건의 원요청·통계검정·실제 적용 임계값을 독립적으로 재계산한 것은 아니다.

우리 자체 특징의 `|z|>2`는 **평소보다 큰 변화가 나타난 비율을 만드는 규칙**이다.
그 기준이 장애 정답이나 사용자의 서비스 수준 목표를 정의하는 것은 아니다.[L3]

## 2. 판단 범위와 실제 필요한 데이터

| 판단할 질문 | 필요한 근거 | 이것만으로는 부족한 것 |
|---|---|---|
| 사용자가 실패를 경험했는가? | 진입 API의 성공률·지연, 평가 기간, 적용 기준 | CPU 상승만 관찰 |
| 원인 후보가 어디인가? | 서비스별 metrics·logs·traces, 식별자와 시각, 관측 누락 정보 | 사용자 API 전체 성공률만 관찰 |
| 정답과 맞았는가? | 주입/사건의 대상·유형·시각, 평가 단위 | 모델 점수 자체 |
| 어떤 전파 관계인가? | 호출 방향·시각·부모 참조와 관계 정답 | 두 서비스가 동시에 느려짐 |

**100% → 100%**다. 따라서 “시스템 장애 사례”가 곧 “모든 API 실패”는 아니다.
어느 서비스가 시작점인지는 그 성공률만으로 결정할 수 없다.

진단 모델에는 관측 데이터를 넣는다. 정답을 드러내는 `injection_name`,
`display_config`, `engine_config`, `ground_truth`는 채점·분류·감사 자료이며
입력 특징으로 넣지 않는다. 파일 이름에도 대상 서비스·고장 종류가 들어 있다.

## 3. 무엇을 맞혔기에 점수가 높았는가?

기존 TT 200회 보정에서 DiagMLP 복원본의 **98.64%는 장애 창만 대상으로 한
원인 1순위 정확도**다. 탐지에서 놓친 장애도 실패로 치면 **95.43%**다.
분모는 장애 창 686개이지 서로 다른 장애 686건이 아니다.[L1]

확인된 해석 조건은 다음과 같다.

- 같은 주입 사건의 다른 시간창이 학습과 검증에 들어갔다.
- 서비스 후보와 배치가 고정되어 있으며, 원형 DiagMLP는 노드 위치를 사용한다.
- 검증 점수로 선택한 모델의 검증 결과이며, 독립 최종시험 결과가 아니다.

따라서 계산이 틀렸다는 뜻은 아니지만 **새 사건 진단 능력으로 확대 해석할 수 없다.**
공유 사건이 정확도를 얼마나 높였는지는 아직 수치로 분리하지 않았다.
높은 점수만으로 데이터가 쉽다거나 모델이 원인 전파를 이해했다고 단정하지 않는다.

우리 자체 상대 특징 모델도 별개로 구분한다. 사건 균등 검증 Top-1은
SN 80.42→89.35%, TT 71.15→75.08%였다. 자체 기준선 대비 개선이지만,
외부 DiagMLP 복원본의 같은 방식 집계 95.52%/98.80%보다 낮았다.
입력 처리·학습 목적이 달라 이 격차를 특정 모듈 하나의 효과로 해석하지 않는다.[L3]

## 4. validation으로 모델을 고르는 것은 잘못인가?

**아니다. 검증 자료로 학습 종료 시점·설정을 선택하는 것은 정상적인 절차다.**
학습 자료로 가중치를 맞추고, 검증 자료로 선택하고, 선택에 사용하지 않은
시험 자료로 최종 성능을 측정한다. 문제는 선택한 검증 점수를 최종 성능처럼
쓰거나, 같은 사건의 창을 양쪽에 배치하거나, 시험 결과를 보며 다시 고르는 것이다.

“검증을 쓰지 않는 고정 5회 학습”이 자동으로 더 타당한 것도 아니다.
별도 관계 탐색은 제한된 계산 예산의 고정 최종 모델 실험이었다.
우리 200회 상한·검증 선택 실험과 합쳐 해석하면 안 된다.[L3,L4]

## 5. 기존 실험을 다시 해야 하는가?

**새 사건에 대한 결론을 내려면 관련 학습·평가는 다시 해야 한다.**
단순히 기존 가중치를 새 시험 분할에 대입해서는 안 된다.
새 시험 사건이 이전 가중치나 전처리 통계에 이미 들어갔을 수 있기 때문이다.

새 분할의 학습 부분만으로 정상 기준·스케일러·학습용 템플릿 등을 다시 맞추고,
모델을 새로 학습하며, 같은 선택 기회를 준 비교 방법도 함께 평가한다.
반면 원자료 획득·해시 검사·변하지 않은 파서 검증까지 모두 반복할 필요는 없다.
단위 검사는 파서·채점기 검증이고, 여기서 필요한 재시험은 **연구 성능 평가**다.

## 6. 데이터 확인 다음에 분할하는 절차

`과제/정답 정의 → 사건·반복·관측 감사 → 분할 단위 협의 → 분할 고정`
`→ TRAIN 전용 처리 → 학습/검증 선택 → 잠근 최종 평가`가 맞다.

사건 ID만 다르다고 독립이라고 보지 않는다. 동일 수집 세션, 반복 주입 구성,
관측 중복과 시간 구간을 함께 본다. 분할 후에는 정상 참고 자료도 같은 경계를 지킨다.
이번에는 분석용 반복 그룹만 만들었고, train/validation/test 배정은 하지 않았다.

## 7. “숫자로 변환”은 선행연구 처리인가, 자체 계산인가?

둘 다 존재하며 단계가 다르다.

| 입력 | Eadro 계열의 확인된 처리 | 우리 자체 MLP 처리 |
|---|---|---|
| metrics | 7개 시계열 → 시간 합성곱 → 시간 풀링 | 정상 기준 대비 변화의 요약 |
| traces | 서비스별 초당 평균 span 지연 → 시간 인코더 | 지연과 span 수를 함께 사용 |
| logs | Drain 템플릿 → 창별 Hawkes baseline → 임베딩 | 기존 18개 특징 실험에서는 미사용 |
| 서비스 문맥 | Eadro 그래프 / DiagMLP 전역 결합 | 관측된 후보들에 대한 상대 차이 |

자체 방법은 9개 채널마다 signed-log 변화 평균과 `|z|>2` 비율을 만들어
**18개 수치 특징**을 계산했다. 관측 마스크·관측률도 사용했다.
이것은 원자료를 숫자 자료형으로 읽은 것에 그치지 않고 **자체 특징 설계**다.[L2,L3]

학습해서 고정하는 정상 기준·스케일러·템플릿은 TRAIN 경계를 지켜야 한다.
반면 원방법이 정한 창별 Hawkes 추정처럼 각 입력 창 내부에서 수행하는 변환은
그 창의 처리이며, 전체 자료로 정상 통계를 맞추는 것과 구분한다.

## 8. 선행 방법을 어느 수준까지 재현해야 하는가?

**핵심 메커니즘은 보존하고, 필요한 수정은 경계와 이유를 밝혀야 한다.**

- Eadro: 모달리티별 시간/Hawkes 처리, 모달리티 결합, 그래프 처리,
  탐지·위치 공동 학습을 보존한다.
- DiagMLP: 모달리티 임베딩과 위치 정보의 결합, 모든 노드의 순서 있는 결합,
  학습 목적을 보존한다. “서비스별 독립 MLP”로 바꾸면 다른 방법이다.[P2]
- 공개 코드의 런타임 오류나 잘못된 채점은 고칠 수 있다. 하지만 시간창·분할·
  정규화·채점 수정은 공통 적용하고 기록해야 한다.

실행본·정확한 설정·분할까지 확인한 **원결과 재현**, 핵심 구조를 구현한
**명시적 복원**, 일부 입력/모듈을 교체한 **변형 비교**를 구분한다.
현재 DiagMLP는 논문 수식 기반 복원이다. 공개 근거만으로 저자의 정확한
GLU 연결 위치와 모든 설정을 복구했다고 주장하지 않는다.[L2]

## 9. tanh 시간 풀링과 Transformer는 어떻게 다른가?

비교 대상은 활성함수 하나가 아니라 **시간 정보를 결합하는 방식**이다.
확인한 Eadro 구현은 시간 인코더의 출력 \(h_t\)에 대해

\[
a_t=\tanh(w_t^\top h_t+b_t),\qquad z=\sum_t a_t h_t
\]

를 계산한다. 시점별 가중치가 있고 음수도 가능하며, softmax로 합을 1로
맞추지 않는다. 앞의 시간 합성곱이 이미 시간 패턴을 처리하므로
“기존 방법은 시간 관계를 전혀 보지 않는다”는 설명도 틀리다.[L2]

Transformer self-attention은

\[
A=\operatorname{softmax}(QK^\top/\sqrt{d}),\qquad H'=AV
\]

처럼 **각 시점이 다른 시점의 내용에 따라 정보를 가져오도록** 한다.
전체 encoder에는 위치 정보, 다중 head, feed-forward, 잔차 연결과 정규화도 있다.[P6]

다음은 성능 결과가 아니라 구조에서 도출한 **조건부 예상**이다.

- 멀리 떨어진 시점의 순서·선후관계·조합이 원인 구분에 중요하면 도움이 될 수 있다.
- 크고 지속적인 자원 상승만으로 구분되거나 창이 짧으면 추가 이점이 작을 수 있다.
- 누락된 trace, 잘못된 정답, 누락된 오류 상태 정보는 attention으로 복원되지 않는다.
- 학습 사건이 적으면 추가 표현력이 오히려 변동성과 과적합을 늘릴 수 있다.

**우리 18개 요약 특징 MLP에는 이 tanh 모듈이 없다.** 이미 시간축을 요약했기 때문에
Transformer를 붙이려면 시간축 보존부터 바꿔야 한다.
RCABench에서는 HTTP 계열 796건이므로, 먼저 필요한 오류·상태 정보가 입력에
들어오는지 확인하는 것이 직접적이다. Transformer의 우위는 아직 예측할 수 없다.

## 10. 전역 결합과 상대 특징·공유 점수 중 무엇이 적합한가?

DiagMLP는 모든 노드 임베딩을 순서대로 이어 붙인다.
따라서 **이미 전역 정보를 보며 노드 간 비교도 학습할 수 있다**.[P2]
서비스 ID·역할과 배치가 안정적인 환경에서는 그 정보가 유용할 수 있다.
반면 입력 차원이 후보 수와 묶이고, 노드의 순서/정체성이 표현에 직접 들어간다.
이 구조적 특성 자체가 실제 성능 결함의 증명은 아니다.

우리 모델은 관측된 후보의 특징별 평균 \(\bar x\)에 대해
\[
s_i=f_\theta(x_i,\ x_i-\bar x,\ mask_i,\ coverage_i,\ contextMask_i)
\]
로 같은 점수 함수를 각 서비스에 적용한다.[L3]
상대 차이를 직접 제공하고 가중치를 공유한다는 **학습 편향**이 차이다.
ID 특징이 없고 후보와 마스크를 함께 재배열하면 점수도 같은 순서로 재배열된다.
하지만 이름을 안 쓴다고 실제 역할·패턴에 대한 의존까지 사라지는 것은 아니다.

이 방법은 평균에 의한 정보 손실, 여러 서비스가 함께 변할 때 상대 차이가 작아지는
문제, 호출 방향을 알지 못하는 한계가 있다. 전역 결합보다 항상 낫다고 할 수 없다.
관계 실험의 caller/callee 평균 문맥은 또 다른 확장으로, 기존 상대 모델과 구분한다.[L4]

**현 단계 판단:** 상대·공유 점수는 검증할 가치가 있는 후보지만 선택이 끝난 방법이 아니다.
같은 입력과 사건 분할에서 DiagMLP, 자체 local, 상대 모델을 비교해야 한다.
시간 encoder 교체와 노드 결합 교체를 동시에 하면 어느 쪽의 효과인지 알 수 없다.

## 11. TVDiag와 DeepHunt는 무엇을 하며 데이터는 어떻게 다른가?

| 방법 | 핵심 처리와 목표 | 원문 자료 및 적용 조건 |
|---|---|---|
| TVDiag | metric/trace/log에서 alert 추출, 그래프 표현, 과제별·교차 모달 contrastive 학습; 원인 instance와 고장 종류 공동 예측 | v3 기준 GAIA, AIOps-22, Sockshop. instance 수 10/40/21, 고장 종류 5/9/7 |
| DeepHunt | 정상 동작 그래프를 graph autoencoder로 학습; 재구성 오차와 전파 패턴을 결합해 위치 진단, 사용자 피드백으로 보완 | D1 전자상거래 46 instance/210 failure, D2 은행 18 instance/133 failure. 서비스와 host 관계도 사용 |

표의 수치는 논문 기재이지 이번에 확보·검사한 사건 수가 아니다.
DeepHunt D1의46개는 서비스 instance40개+VM6개이며,
§5.1은 은행 D2 원자료를 비공개라고 명시한다.[P4]

TVDiag의 metric 3-sigma, trace Isolation Forest, log 규칙은 **alert 추출**이다.
그것이 곧 사용자 실패 정답인 것은 아니다. F1은 주로 **고장 종류 분류**의 지표다.[P3]
DeepHunt는 장애 탐지 자체가 아니라 장애가 주어진 뒤의 위치 진단을 다룬다.
정상 자료 학습과 피드백을 이용하는 전체 구조를 단순한 지도 GNN으로 바꾸면 안 된다.[P4]

둘 다 단순히 Eadro의 다른 이름이 아니다. service와 instance를 맞추는 매핑,
TVDiag의 alert 필드·종류 라벨, DeepHunt의 정상 자료·배치 관계를 확인해야 한다.
우리 18개 요약값만 넣고 원형 방법을 비교했다고 하면 부정확하다.

## 12. 왜 F1, Top-k, MRR 등을 쓰는가?

| 과제 | 지표 | 답하는 질문 |
|---|---|---|
| 장애 유무 탐지 | precision, recall, F1, FP/FN | 경보가 맞는가, 장애를 놓치는가 |
| 원인 서비스 순위 | Top-1, Top-3, MRR | 몇 번째 점검에서 정답을 찾는가 |
| 고장 종류 분류 | 명시한 평균 방식의 F1, 혼동행렬 | 어떤 종류를 혼동하는가 |
| 원인 집합 | any-hit와 set recall 등을 분리 | 하나만 찾았는가, 필요한 대상을 모두 찾았는가 |
| 방향 있는 관계 | endpoint+direction 일치 | 올바른 두 끝점과 방향을 찾았는가 |

\(F1=2TP/(2TP+FP+FN)\)이며, \(MRR=mean(1/rank)\)다.
Top-1은 첫 점검의 성공, Top-3은 세 후보까지 확인할 때의 성공률이다.
정상 자료를 많이 맞히는 것과 원인을 찾는 것은 다르므로 분모를 섞지 않는다.
Eadro의 탐지 F1과 TVDiag의 고장 종류 F1도 같은 점수가 아니다.[P1,P3]

한 사건을 많은 창으로 만들었다면 창 평균만으로 큰 사건의 비중을 늘리지 않는다.
사건 균등 집계, 종류/관측 상태별 결과, 반복 학습의 변동성을 함께 본다.
원인 두 개 중 하나만 맞힌 any-hit를 “원인을 전부 찾음”으로 표시하지 않는다.

## 13. 학습과 평가를 분리해 다시 구성하자는 뜻

찬성한다. **원자료·사건을 먼저 정하고 분할한 다음, 각 학습 부분에 맞춰 처리와
모델을 새로 학습**하는 방식이어야 한다. 모든 자료로 만든 정규화값을 재사용하거나
모든 사건을 본 기존 checkpoint를 새 분할의 모델이라고 부르면 안 된다.

비교할 연구 방법에도 동일한 사건·정답·평가 기회를 준다.
관측 부족 사례를 모델 성능에 따라 제외하거나 잘 맞는 고장 종류만 남기지 않는다.
이번 분석은 그 재구성을 위한 근거이며, 실제 재학습은 아직 하지 않았다.

## 14. Eadro 데이터를 다시 쓰면 안 되는가? 구실험을 폐기한다는 뜻은?

**다시 쓸 수 있다. 이전 설명이 영구 사용 금지처럼 들렸다면 잘못된 설명이다.**
원자료를 사용해 새 그룹 분할·학습 전용 처리·새 모델 학습으로 재분석할 수 있다.
다만 이미 분석한 자료를 처음 보는 맹검 자료처럼 표현하지 않아야 한다.

“구실험 폐기”는 원자료나 검증된 코드를 삭제한다는 뜻이 아니다.
기존 고득점을 새로운 사건 일반화의 최종 증거로 쓰지 않고,
새 계약에 맞는 결과로 그 결론을 교체한다는 뜻이다.
기존 기록은 무엇을 바꿨는지 비교할 수 있도록 남긴다.

추가 주의: SN/TT에서는 recording별로 root 서비스 묶음이 다르다.
recording을 통째로 빼면 수집 환경뿐 아니라 학습 때 정답으로 본 서비스도 바뀐다.
따라서 recording 분리가 항상 원하는 “같은 서비스의 새 장애” 시험인 것은 아니다.[L4]

## 15. RCAEval의 기존 108/36/36 분할도 바꿀 수 있는가?

**타당성에 문제가 확인되면 합의 후 새 버전으로 바꿀 수 있다.**
기존 lock은 임의 변경을 방지하는 기록이지 분할의 과학적 타당성을 보증하지 않는다.

현재 분할은 system/root/fault 반복 묶음을 함께 배정한 것으로 기록되어 있다.
따라서 Eadro의 창 분할 문제와 동일하다고 미리 결론 내리지 않는다.
사건 중복·정답·시간·훈련 통계 사용·평가 목표를 메타데이터부터 다시 확인하고,
문제가 있으면 이유와 새 manifest를 남겨 관련 모델을 재학습한다.
점수가 마음에 들지 않는다는 이유로 분할을 바꾸지는 않는다.
기존 최종36건의 보호된 원관측은 이번에 열지 않았다.

## 16. RCABench 전체를 분석한 결과

`RCABENCH_REPORT.md`, `metadata_analysis.json`, `verification.json`이 실제 결과다.
1,422건 전부를 포함했고 단일 정답/관측 완전 사례만 골라 분석하지 않았다.
25개 고장 종류, 주입 대상과 정답의 관계, 사용자 영향 요약, 관측 지원,
시간 관계와 구성 반복을 확인했다.

큰 발견은 **정답 두 항목이 반드시 두 개의 독립 고장이나 유일 원인 불명 상태를
뜻하지 않는다는 것**이다. 공개 생성 코드에서는 HTTP/DNS/JVM-MySQL의
실제 동작 선택자가 `app_name`의 pod들을 가리키고, 정답 목록은 영향 대상도 담는다.
따라서 원래 목록 순서를 임의로 택하는 것과 달리, 설정 필드와 선택자 의미로
단일 표적 과제를 구성할 여지가 있다. 실행 revision·실제 활성화 증명은 별도다.

## 17. 원인 서비스 하나, 영향집합, 관계 중 어느 범위가 맞는가?

| 선택지 | 실제 답해야 하는 것 | 이번 자료의 판단 |
|---|---|---|
| A. 주입 표적 서비스 순위 | 장애 조작이 설정된 애플리케이션을 찾음 | 비network 1,168건; 설정/정답 충돌1건을 제외한 1,167건이 검토 후보 |
| B. 원래 정답 서비스 집합 | 원래 benchmark가 인정한 서비스 중 하나/전체를 찾음 | 전체 1,422건에 가능하나 any-hit와 집합 회수를 구분해야 함 |
| C. 방향 있는 주입 관계 | source·target·direction을 맞힘 | network254건에 해당 정보가 있으나 실제 인과 전파 경로의 정답은 아님 |

B의 정답 목록도 **실제로 영향을 받은 모든 서비스의 완전한 집합은 아니다.**
설정에서 생성한 기대 영향/허용 정답이므로 “전체 영향 범위 복원”과 구분한다.
A는 Eadro/DiagMLP의 단일 서비스 순위와 비교하기 가장 직접적이다.
그러나 설정 표적의 복원이지 모든 운영 사고의 유일한 물리적 원인을 증명하는 과제는 아니다.

**제안:** A를 주 과제로 검토하고, B는 원 benchmark 호환 점수,
C는 별도 분석으로 구분하는 구성이 가장 설명하기 쉽다.
1,167건을 학습 자료로 확정하거나 나머지를 버리자는 결정은 아직 하지 않았다.

## 18. 이 근거로 어떤 연구 범위를 상의할 것인가?

협의안은 다음과 같다.

1. **문제:** 사용자 영향이 기록된 장애에서 점검할 서비스 순위를 개선한다.
   복구 실행, 전체 인과 그래프 복원, 경량성 입증을 자동으로 목표에 추가하지 않는다.
2. **정답:** 위 A/B/C 중 주 과제를 먼저 정한다. 추천은 A이며 설정 충돌과
   생성 코드의 적용 가능성을 명시한다.
3. **자료:** RCABench를 주 자료 후보로, Eadro SN/TT를 재분석 자료로 검토한다.
   RCAEval도 기존 분할의 타당성과 입력 적합성에 따라 사용 여부를 판단한다.
4. **방법:** 상대 특징·공유 점수와 Transformer는 서로 다른 가설이다.
   관측/정답 문제를 구조 문제로 오인하지 않고, 한 번에 검증할 변화부터 정한다.
5. **평가:** 사건 단위 분할, 학습 전용 통계, 검증 선택, 잠근 시험을 공통 적용한다.
   기존 방법과 자체 기준선을 분리해 비교하고 개선이 없을 가능성도 허용한다.

**이번 결론은 “어떤 모델을 돌리자”가 아니라,
사용자 영향·주입 표적·평가 정답을 연결할 근거가 확보됐고,
그에 맞춰 과제를 먼저 선택할 수 있다는 것이다.**
