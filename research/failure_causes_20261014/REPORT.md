# 네트워크 장애 원인 서비스 오분류: 제한된 실패 원인 진단

2026-10-14 · 허용 개발 자료 · 새 학습 없음

## 목표와 판정 원칙

목표는 새로운 돌파구를 주장하는 것이 아니라, 좁은 개선 대상을 근거로 정하는 것이다.
현재 질문은 “왜 네트워크 지연·손실 장애에서 원인 서비스 순위가 잘못되는가?”다.
기존 검증 자료를 재분석했으므로 새 독립 검증이나 모델 우수성 평가가 아니다.
수치적 사실과 인과적 설명을 구분한다.

## 결론 요약

**확인된 병목은 “현재 모델이 학습에 사용한 네트워크 장애조차 충분히 구분하지
못한다”는 것이다.** 새로운 root/type 조합의 일반화 문제만으로 설명되지 않는다.

- Directed의 네트워크 Top1은 SN TRAIN 53.22% / validation 46.18%,
  TT 32.73% / 31.38%다. CPU TRAIN은 각각 100.00% / 99.99%다.
- SN은 총 35–40번의 가중치 업데이트만 했다. 마지막 epoch에서도 전체 TRAIN
  online CE가 평균 12.60% 줄어, 최적화가 충분했는지는 확인되지 않았다.
- TT는 360–365번 업데이트했지만 네트워크 TRAIN 오답이 많다.
  적은 학습량 하나로 두 시스템을 공통 설명하는 것도 근거가 부족하다.
- TT root latency 관측은 254/3,451창뿐이다. 반면 관측된 root latency를
  정상 참조 mask가 버린 창은 두 시스템 모두 0이다.

따라서 **전처리 mask 오류를 고치거나 관계 모델을 키우는 것을 바로 처방하지 않는다.**
첫 확인 대상은 고정 입력·모델의 학습량 통제다. 그 효과는 이번에 실험하지 않았다.
이 결과는 단일 인과 원인의 확정이 아니라, 잘못된 설명을 배제하고 다음 확인을 좁힌 것이다.

## 1. 입력 경로에서 확인한 사실

기존 입력은 7개 메트릭(CPU 3, 메모리 2, 수신/송신 bytes 2)과
trace 평균 지연·span 수다. 패킷 손실률이나 재전송 횟수는 별도 입력 채널이 아니다.
각 채널은 10초 창의 signed-log 표준화 편차 평균과 이상 지속 비율로 요약된다.
시간순서는 이 요약에서 보존되지 않는다. 이것은 코드상 사실이며,
시간순서 추가가 성능을 높인다는 실험 결과는 아니다.

### 1.1 정상 참조 때문에 관측된 root latency를 버린 경우는 없다

| 시스템 | 개발 장애 창 | root latency 실제 관측 | 관측됐지만 정상 참조 없어 마스킹 | root 로컬 입력 완전 동일 후보 존재 |
|---|---:|---:|---:|---:|
| SN | 325 | 225 (69.23%) | 0 | 0 |
| TT | 3,451 | 254 (7.36%) | 0 | 0 |

이 수치는 창 개수 집계다. 아래의 사건 균등 평균과 분모가 다르다.
TT에서 정상 latency 참조가 없는 서비스가 있다는 기존 관측은 맞지만,
현재 validation에서 **이미 관측된 원인 지연값을 참조 mask가 지워 오분류했다**는
설명은 지지되지 않는다. 값을 관측하지 못하는 문제가 더 앞에 있다.
없는 참조를 임의로 채우는 것만으로 현재 root latency가 복구되는 것은 아니다.

로컬 입력의 완전 일치도 이번 자료에서 발견하지 못했다.
따라서 정확히 같은 입력을 공유 scorer에 넣는 구조적 동점 문제가 주원인이라는
근거는 없다. 다만 작은 차이가 있다고 해서 정답 식별 정보가 충분하다는 뜻은 아니다.

### 1.2 CPU와 네트워크 장애는 입력에서 드러나는 방식이 다르다

아래 규칙은 결과를 보기 전에 고정한 진단용 probe다.
기존 특징의 signed-log-z 평균 절댓값 중 해당 채널 그룹의 최댓값으로
모든 후보 서비스를 동일하게 점수화한다. 학습·튜닝·root 정보 사용은 없다.
동점은 1/k credit이며, 사건 내 창 평균 후 사건에 동일한 가중치를 준다.

| 시스템·고장 | Directed Top1 | CPU 변화 probe | network bytes probe | latency probe | 전체 채널 probe |
|---|---:|---:|---:|---:|---:|
| SN CPU | 99.75% | 96.48% | 7.01% | 20.19% | 96.48% |
| SN 지연 | 51.91% | 8.97% | 6.06% | 33.46% | 37.14% |
| SN 손실 | 40.44% | 10.99% | 0.00% | 15.70% | 18.65% |
| TT CPU | 99.97% | 100.00% | 3.36% | 3.80% | 99.31% |
| TT 지연 | 37.74% | 4.21% | 31.66% | 10.90% | 31.95% |
| TT 손실 | 25.02% | 4.99% | 25.02% | 5.06% | 24.87% |

CPU 장애는 원인 서비스의 CPU 편차가 큰 간단한 단서로 거의 설명된다.
반면 “가장 크게 이상해진 서비스=원인”이라는 같은 형태의 규칙이
네트워크 장애에 그대로 성립하지는 않는다.
TT 손실에서 network bytes probe와 모델 점수가 유사하다는 사실만으로
모델이 그 규칙을 그대로 학습했다고 단정할 수 없다. 서로 맞힌 창도 다르다.

모델이 놓치고 network bytes probe가 맞힌 기대 credit은
TT 지연 6.53%p·손실 7.09%p다. 반대로 모델만 맞힌 credit은
각각 12.62%p·7.09%p다. 단순 probe로 대체하면 해결된다는 결론은 아니다.
개별 probe의 결과만 보고하며 정답을 보고 여러 probe 중 하나를 선택한
oracle 점수는 만들지 않았다.

### 1.3 trace와 10초 평균의 한계를 구분한다

root latency가 사용 가능한 창 비율의 **사건 균등 평균**:

| 시스템 | CPU | 지연 | 손실 |
|---|---:|---:|---:|
| SN | 100.00% | 64.57% | 42.18% |
| TT | 7.76% | 10.80% | 3.26% |

TT 네트워크 장애는 원인 서비스의 latency를 직접 비교할 기회 자체가 적다.
하지만 CPU는 trace가 드물어도 잘 맞힌다. 따라서 **trace가 적으니 모든 실패가
설명된다**는 주장은 맞지 않는다. 어떤 장애에 어떤 정보가 필요한지 분리해야 한다.

10초 signed 평균의 양·음 변화 상쇄도 측정했다. TT network bytes는
해당 상쇄율이 0이고, latency의 사건 평균 상쇄율도 TT 지연·손실에서 0.1% 미만이다.
이는 관측된 원인 네트워크 채널에서 **signed 평균 상쇄**를 우선 원인으로
지목할 근거가 약하다는 뜻이다. peak·시점·순서 소실 전체가 없다는 증거는 아니며,
미관측/무편차 채널의 상쇄율을 0으로 정의한 전체 평균이라는 제한이 있다.

## 2. 학습 상태와 평가 조건

54개 고정 최종 checkpoint를 TRAIN/validation에서 추론했다.
validation logits는 기존 저장값과 54/54개 모두 완전히 같았다.

### 2.1 학습한 네트워크 사건에서도 실패한다

| 시스템·고장 | TRAIN Top1 | validation Top1 |
|---|---:|---:|
| SN CPU | 100.00% | 99.75% |
| SN 지연 | 55.11% | 51.91% |
| SN 손실 | 51.34% | 40.44% |
| TT CPU | 99.99% | 99.97% |
| TT 지연 | 39.27% | 37.74% |
| TT 손실 | 26.18% | 25.02% |

TRAIN 사건은 두 fold에 등장하므로 창→seed/fold→사건 순으로 평균해
독립 사건으로 두 번 세지 않았다. validation은 각 사건의 held-out fold다.
같은 사건을 서로 다른 모델·학습 지원에서 평가하므로 이 차이는
동일 모델의 짝지어진 일반화 오차나 원인별 오차 분해가 아니다.
그 한계를 지켜도 **네트워크 오분류가 이미 학습 지지집합에 존재한다**는 사실은 남는다.

### 2.2 5 epoch라는 숫자만으로 학습량이 같다고 볼 수 없다

| 시스템 | fold별 TRAIN 장애 창 | 총 업데이트 | Directed online CE4→CE5 평균 상대 감소 |
|---|---|---|---:|
| SN | 217 / 227 / 206 | 35 / 40 / 35 | 12.60% |
| TT | 2,292 / 2,278 / 2,332 | 360 / 360 / 365 | 2.76% |

업데이트 수는 보존된 TRAIN 행 수와 batch32·5epoch 학습 루프로 재구성했다.
별도 optimizer telemetry를 관측한 값은 아니다.
54개 모든 run의 4→5 online CE가 감소했다.

이 CE는 epoch 중 계속 바뀌는 모델의 손실 평균이며, 고정 checkpoint CE와 다르다.
또 CPU와 네트워크를 합친 손실이므로, 감소만 보고 네트워크 순위가 계속
개선되고 있다고 말할 수 없다. SN의 부족한 최적화 가능성은 남지만,
학습 연장이 실제 원인 서비스 순위를 개선할지는 별도 대조가 필요하다.

### 2.3 평가 조건이 요구하는 것은 root별 다른 고장 유형으로의 전이다

각 서비스에는 고장 유형별 사건이 하나씩 있다. 각 fold에서 같은 root의 두 유형을
TRAIN에 넣고 남은 한 유형을 validation에 둔다. 따라서 새 root 자체를 시험하는
조건이 아니라 **root별 미학습 고장 유형**을 시험하는 조건이다.
그 유형은 다른 root의 TRAIN에는 존재할 수 있다.

TRAIN root당 장애 창은 SN 14–24개, TT 66–97개이며 각각 두 사건이다.
사건 수가 적고 recording도 공유하므로 실제 새 수집 환경으로의 일반화를 입증하지 않는다.
다만 TRAIN 오답이 이미 많으므로 고장 유형 전이만 실패의 전부라고 볼 수는 없다.

## 3. 무엇을 확인했고 무엇은 아직 모르는가

| 후보 설명 | 이번 근거 | 판정 |
|---|---|---|
| 정상 참조 mask가 관측된 root latency를 지웠다 | validation 0/3,776창 | 이번 root latency 실패 설명으로 지지 안 됨 |
| root와 다른 후보의 입력이 완전히 같아 구분 불가 | 로컬 입력 완전 일치 0창 | 정확 일치에 의한 강제 동점 설명은 지지 안 됨 |
| 처음 보는 root/type 조합에서만 실패한다 | TRAIN 네트워크 Top1도 53.22% / 32.73% | 충분한 설명이 아님 |
| 가중치 업데이트가 부족하다 | SN 35–40회·마지막 online CE 감소 | 가능한 설명, 개선 효과 미검증 |
| 네트워크 단서가 부족하거나 현재 표현이 활용 못 한다 | TT latency 희소, 단순 편차 probe 약함, 높은 TRAIN 오답 | 두 설명을 분리하지 못함 |
| 호출 관계를 추가하면 해결된다 | 기존 TT 효과 작음, 이번에 관계 개입 없음 | 해결책으로 확정할 근거 없음 |

낮은 probe 점수는 이 고정 규칙의 한계이지 정보론적 식별 불가능성의 증명이 아니다.
반대로 probe만 맞히는 창의 존재도 새 모델의 개선을 보증하지 않는다.

## 4. 좁은 다음 확인과 개선 목표 — 제안만

**연구 목표 후보:** 네트워크 지연·손실의 root-service Top1/Top3를 개선하되,
CPU 성능을 유지하고 추가 계산 비용을 함께 보고한다.
첫 번째 통제는 모델을 바꾸는 것이 아니라 **현재 입력·현재 모델에서 학습량 부족을
분리하는 것**이다. 특히 SN은 업데이트 수가 작으므로 이 확인을 먼저 하는 편이 합리적이다.

후속 실험을 승인받으면 입력·분할·모델·optimizer·seed를 고정하고 학습 budget만
바꾸는 제한된 비교를 사전에 정한다. 정지 규칙·상한·선택 기준은 실행 전에 고정하고,
validation 결과를 보고 epoch를 계속 고르지 않는다.
TRAIN 고정 checkpoint CE와 유형별 Top1, validation 유형별 Top1/Top3/MRR,
추가 업데이트 수와 시간을 함께 기록한다.

- TRAIN과 validation 네트워크 점수가 함께 개선되면 학습 budget의 기여를 지지한다.
- TRAIN만 개선되면 현재 평가에서 일반화 개선으로 주장하지 않는다.
- 둘 다 개선되지 않으면 그 특정 budget 변경의 효과가 없다는 뜻이다.
  모든 최적화 가능성을 배제하거나 곧바로 정보 부족을 확정하지 않는다.

이 통제 후에도 실패가 남을 때 한 부분의 입력/표현 개선을 선정한다.
현재 결과를 근거로 그래프 확대·새 데이터 수집·새 모델을 자동 시작하지 않는다.
최종 연구 기여는 학습 epoch 증가 자체라고 미리 정하지 않는다.
