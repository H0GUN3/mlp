# 마이크로서비스 장애의 원인 서비스 순위 개선
## 연구 배경·관련 연구·현재 증거·다음 판단을 위한 인수인계 보고서

**기준일: 2026-10-16.** 이 연구를 처음 접하는 동료 연구원을 위한 문서다.
**현재 상태: 권고 실행 보류.** 모델·주 자료의 선택은 아직 합의되지 않았다.
최신 [실제 데이터 흐름·평가 타당성 확인](DIAGMLP_DATAFLOW_AND_VALIDITY.md)이 후속 설명의 기준이다.
**후속 질문 반영:** 모델 명칭·높은 점수·자료 역할에 관한 [15개 설명과 협의안](CLARIFICATIONS.md)을 함께 읽는다.
경량화는 연구 목표가 아니며, CPU 오류만을 유일한 연구 문제로 정하지 않는다.
논문별 상세한 방법·자료·비교군·관련연구·원문은 [LITERATURE.md](LITERATURE.md),
주장 검토와 접근 제한은 [EVIDENCE.md](EVIDENCE.md)에 정리했다.
`[S번호]`는 문헌 상세의 식별자, `[L번호]`는 마지막의 로컬 근거다.

## 0. 먼저 알아야 할 결론

**연구 목표는 장애가 발생했을 때 실제 원인 서비스를 조사 목록의 더 앞에 놓는 것이다.**
전체 AIOps 플랫폼, 자동 복구, 모든 장애의 인과관계 복원을 만들려는 연구는 아니다.

| 구분 | 현재 말할 수 있는 내용 |
|---|---|
| 실제 문제 | 산업 현장에서 원인 서비스/리소스의 조사 우선순위를 결정하는 문제가 존재한다. 실제 운영 장애를 평가한 연구가 이를 뒷받침한다. [S01,S09,S14] |
| 우리에게 확인된 현상 | TT 사건 분할 개발 평가에서 **DiagMLP 복원 기준 모델**의 Top1은86.56%, Top3는99.74%다. 제안 모델의 점수가 아니다. CPU Top1은77.81%다. [L01,L03] |
| 아직 모르는 것 | 왜 실제 원인보다 다른 서비스를 높게 평가했는지, 어떤 변경이 이를 줄일지, 다른 환경에도 같은 문제가 나타나는지다. |
| 진행하지 않는 후보 | 관측 span 개수 추가는 사전 추진 조건을 충족하지 못해 학습하지 않았다. 효과 없음이 입증된 실험과는 다르다. [L04] |
| 현재 조치 | 기존 권고 실행을 보류하고 원문 역할·실제 데이터 흐름·사건 공유 평가·정답 단위를 먼저 확인한다. MLP와RCABench를 최종 선택했다고 간주하지 않는다. |

**현 단계는 ‘과거 창 분할의 자체 모델 점수 차이 기록, 방법론 기반 비교 모델 확보,
후속 count 가설 보류’다. 과거 창 분할은 검증 사건이 학습에도 등장하므로
새 사건의 개선 근거에서 제외한다. 독립 일반화·논문 기여는 아직 입증하지 않았다.**

## 1. 배경: 어떤 운영 문제를 다루는가?

### 1.1 이상을 찾는 일과 원인을 찾는 일은 다르다

여기서 사용하는 자료는 세 종류다.

- **지표(metric):** CPU·메모리·지연 등 시간에 따른 수치.
- **로그(log):** 서비스가 남긴 실행·오류 기록.
- **트레이스(trace):** 요청 처리 과정의 서비스 호출 기록. 그 안의 개별 작업 기록이 span이다.

서비스는 논리적 기능 단위이며, 같은 서비스가 여러 실행 인스턴스로 배포될 수 있다.
여러 곳에서 이상이 관측되더라도 그 모두가 최초 원인은 아니다.
그래서 “어디가 이상한가”와 “어디부터 원인 조사를 시작할 것인가”는 별도 과제다.
실제 운영 연구는 호출·배치 관계와 관측 정보를 이용해 이 우선순위를 제공한다. [S01,S09,S13]

### 1.2 이 문제가 실제라는 근거

가상의 장애 사례를 연구 필요성으로 사용하지 않는다.

| 실증 연구 | 실제 평가 자료 | 이 보고서에서 근거로 사용하는 범위 |
|---|---|---|
| Groot, ASE2021 | eBay 운영 장애952건 | 실제 운영자가 확인한 원인 event를 자동 순위화하는 과제가 존재한다. |
| MicroHECL, ICSE-SEIP2021 | Alibaba 실제 장애75건, 별도 온라인 적용600여건 | 서비스 단위 진단이 실제 운영에서 평가됐다.75건의 HR@1은48%, HR@3는67%였다. |
| LagRCA, FSE2026 Industry | 은행 시스템146사건 | 원인과 영향 인스턴스의 이상 시작에 수분 차이가 나타나는 사건이 실제로 관측됐다. |

위 연구들의 점수를 서로 비교해 가장 좋은 방법을 정하려는 표가 아니다.
HR@1은 정답 원인이 첫 후보인 사건 비율, HR@3은 첫 세 후보 안에 있는 사건 비율이다.
HR@3에는1·2·3위가 모두 포함되며 장애 복구 성공률이 아니다.
이 MicroHECL은 우리가 복원·평가한 모델이 아니다. 산업 결과48/67%와
아래 DiagMLP 복원 기준의TT 점수를 크기만으로 비교해서는 안 된다.
운영 자료를 우리가 직접 재검증한 것도 아니며, 원문에 보고된 평가 근거다.
출력 단위·관측 자료·정답·평가 시점이 다르다.
**확인되는 것은 ‘원인을 우선순위로 제시하는 문제가 실제 운영 과제’라는 사실이다.**
우리 모델이 그 현장 문제를 이미 해결했다거나 복구시간을 줄였다는 증거는 없다.

### 1.3 우리가 해결 대상으로 좁힌 부분

현재의 과제는 다음과 같다. **협의안은 MLP를 기본 학습 모델로 유지하되
최종 제안 구성을 아직 확정하지 않는 것**이다.
구체적으로 자체 local/relative 서비스 점수기를 출발점으로 삼고,
DiagMLP/Eadro 복원본은 외부 비교 기준으로 구분한다.
경량화가 아니라 관측을 어떻게 표현·비교·점수화하는지의 효과를 묻는다.
LLM이나 더 복잡한 그래프 모델의 추가를 미리 정하지 않는다.

> **장애가 발생했다는 조건에서, 정해진 후보 서비스들의 지표·로그·트레이스를 이용해
> 실제 원인 서비스를 가능한 한 앞에 배치한다.**

입력은 원인 정답을 포함하지 않는 관측 자료, 출력은 서비스별 점수와 순위다.
정답은 평가와 지도학습에만 사용한다.
서비스를 찾은 뒤의 코드 버그 설명, metric 수준 원인 규명, 자동 복구는 범위 밖이다.
새로운 서비스가 추가되는 가변 후보 문제도 현재의 주 목표가 아니다.

지표의 의미는 다음과 같다.

- **Top1:** 정답이 첫 후보인가.
- **Top3:** 정답이 첫 세 후보 안에 있는가.
- **MRR:** 정답 순위의 역수 평균. 정답을 더 앞에 둘수록 높다.

현재는 창별 점수를 사건 안에서 평균하고 사건에 같은 가중치를 준다.
창이 많은 장애가 결과를 독점하지 않도록 한 것이다. [L02,L03]
이하 fold는 교차검증의 분할, seed는 무작위 초기값,
checkpoint는 학습 중 저장한 모델 상태를 뜻한다.

## 2. 왜 이 연구 주제와 비교 방법을 선택했는가?

### 2.1 선택 이유

1. **문제의 실재성이 있다.** 실제 운영 사건을 대상으로 원인 조사 순위를 평가한 연구가 있다.
2. **작은 개선을 측정할 수 있다.** 입력·후보·학습·평가 조건을 고정하고 한 부분만 바꾼 뒤 순위와 비용을 비교할 수 있다.
3. **이미 확보한 방법 기반 모델에 잔여 오류가 있다.** 전체86.56% 대99.74%라는 Top1/Top3 차이를 실제 개발 자료에서 측정했다.
4. **‘MLP 대 GNN’이라는 큰 우열 논쟁을 피할 수 있다.** 중심 질문은 특정 오류 조건과 한 변경의 추가 효과다.

3번은 아직 보편적 산업 결함이 아니다.
**산업 문헌은 문제의 존재를, 우리 실험은 현재 조건의 잔여 오류를 각각 뒷받침한다.**
두 근거를 연결하되 같은 오류 원인이라고 단정하지 않는다.

### 2.2 중심 비교군

| 방법 | 우리가 선택한 이유 | 이번 연구에서 맡는 역할 |
|---|---|---|
| **DiagMLP, Eadro 기반** | 같은 원인 서비스 순위를 다루는 기존 MLP 방법이며 앞단까지 포함한 강한 비교가 가능하다. | 자체 제안과 비교할 외부 기준. 제안 모델이 아님 |
| **Eadro** | 같은 계열의 입력과 탐지·위치 진단 목적을 사용한다. | 그래프 처리 기준. 다른 구조에서도 같은 현상이 나타나는지 확인 |
| **BARO, 선택 사항** | 학습형 모델이 단순한 정상 대비 편차보다 나은지 확인할 수 있다. | 비학습 보조 기준. 다중모달 모델과 동일한 방법이라고 부르지 않음 |

선정 이유는 **방법론의 직접 비교 가능성**이지, 유리한 성능 차이를 만들기 위해서가 아니다.
자체 MLP의 변경 효과는 동일한 자체 기준선과 비교하되, 그것만으로 출판 방법보다 좋다고 하지 않는다.
저자 모델의 소스 코드를 반드시 개조해야 하는 연구도 아니다.
향후 개선이 전파 보정·공유자원·시간차를 다룬다면 AnoProp/LatentScope/LagRCA 등
해당 변경에 더 가까운 방법을 추가 검토해야 한다.
지금의 두 기준만으로 모든 최신 연구보다 우수하다고 주장할 수는 없다.

### 2.3 복원 기준 모델과 자체 제안 원형을 구분한다

여기의 모델은 **현재 TT에서 평가한 DiagMLP/Eadro 복원 기준 모델**이다.
아래는 그중 DiagMLP 복원의 구조이며 자체 relative 제안 원형이 아니다. [L02,L06]

```text
지표·로그·트레이스
  → 시간 정렬과 모달별 전처리
  → 기존 방법의 모달별 인코더
  → 서비스별 세 표현과 서비스 위치 벡터
  → Modal Fusion: 같은 서비스의 자료 결합
  → 모든 서비스 표현을 이어 붙임
  → Node Fusion: 시스템 전체 표현 생성
  → 탐지 head / 원인 서비스 점수 head
```

Eadro는 결합 이후 그래프·pooling을 사용하고, DiagMLP 복원은 논문식의 fusion을 사용한다.
두 모델 모두 앞단의 관측 처리와 학습 목적을 유지했다.
따라서 **이 두 복원 기준 모델**은18개 수치 특징을 쓰는 자체 local/relative MLP와 다르다.
local은 내부 기준선이고 relative는 실험 제안 원형이다. 최종 논문 제안법으로 확정된 것은 아니다.

### 2.4 이번 연구의 재현 기준

**원 논문의 환경·모든 데이터·모든 점수를100% 맞추는 것은 목표가 아니다.**
사용자와 합의한 기준은 핵심 방법론과 처리 흐름을 크게 바꾸지 않고 구현하는 것이다.

- 전처리·인코더·결합·head·학습 목적의 핵심을 보존한다.
- 공개 수정 코드 사용, 비공개 설정의 대체값, 층폭·dropout·분할·선택 규칙을 공개한다.
- 저자 통합 코드와 정확히 같은 구현이라고 과장하지 않는다.
- 원 논문과 점수가 다르다는 이유만으로 실패라고 하지 않는다.
- 반대로 구현 오류나 부적합한 평가 조건을 “환경 차이”로 덮지도 않는다.

현재 코드 경로와 기존 검증 버전의 일치, 핵심 처리 보존은 확인했다.
논문과 다른 부분은 선언된 구현 선택이다. 원 논문 점수 맞추기를 위한 추가 실험은 요구하지 않는다.
다만 Eadro의 초기 checkpoint 선택 현상은 현재 결과 해석의 제한으로 남는다. [L01,L02,L05,L06]

## 3. 관련 연구는 어떤 해법을 제시했는가?

전체 상세는 [논문별 조사](LITERATURE.md)에 있다.
각 카드에 문제·처리·자료·비교군과 선택 이유·관련연구 연결·한계를 담았다.
다음 표는 연구 목표와 연결하기 위한 지도다.

| 연구 흐름 | 대표 연구 | 확인·보고한 결론 | 한계와 우리에게 필요한 판단 |
|---|---|---|---|
| 여러 관측의 결합 | Eadro, DiagFusion, TVDiag |각자의 평가에서 다중 관측·표현·공동/과제별 학습의 효과를 보고했다.|주입/라벨/출력 단위가 달라 우리 자료의 성능을 보장하지 않는다. 단순 모달 추가는 이미 존재한다.|
| 모델링의 추가 기여 | DiagMLP |일부 benchmark에서는 앞단을 유지한 MLP가 GNN의 대안이 됐다.|모든 GNN 열등성은 아니다. 복합 교체·고정 후보·표 불일치가 남는다.|
| 정상 학습과 피드백 | DeepHunt |정상 자기지도와 root 피드백을 결합한 진단을 평가했다.|정상/피드백·관계 정보 예산과 서비스 외 후보까지 고려해야 한다.|
| 통계·의존 그래프 | BARO, MicroRCA, TraceRCA |통계·trace·그래프 기반 진단도 유효한 기준이 될 수 있다.|탐지 시점·정상 참조·수집과 분할에 의존하며 모든 전파 혼동을 해결하지 않는다.|
| 내부/외부 증상·상대정보·prior 통제 | PRISM, controlled MLP/PSC-GRCA |관측 의미·상대 정보·대상 빈도를 분리해야 모델 효과를 해석할 수 있다.|의미적 가정·benchmark 편향·preprint 검증 범위가 남는다. 상대 특징 자체가 새 기여는 아니다.|
| 인과·잠재 리소스 | CausalRCA, LatentScope, AnoProp |metric과 원인 resource를 구분하는 접근과 공유자원 보정이 제시됐다.|조건부 metric 진단을 서비스 찾기 성능으로 바꾸거나 관측 그래프를 인과 증명으로 읽으면 안 된다.|
| 이질성·전파 범위·시간차 | CHASE, LagRCA |관계의 이질성·고차 구조·시간차를 고려한 진단을 평가했다.|우리 TT 오류가 같은 이유라는 증거는 없고 후보·정답·분할도 다르다.|
| 산업 운영 진단 | Groot, MicroHECL |실제 운영에서도 원인 추천이 활용·평가됐다.|오답은 남으며 조직·자료·정답 단위가 달라 현장 효과를 우리 점수로 대신할 수 없다.|

### 3.1 관련연구의 연결 관계

```text
단일 지표·로그·trace 진단
  ├─ 자료 결합: DiagFusion / Eadro / TVDiag
  │    └─ 모델링 기여 점검: DiagMLP
  ├─ 정상 학습·피드백 순위: DeepHunt
  ├─ 단순 변화 점수: BARO
  ├─ 회귀·원인 리소스: CIRCA → LatentScope → AnoProp
  └─ 관계·전파 모델: MicroHECL / CHASE / LagRCA
```

이는 논문 간 모든 역사적 계보를 주장하는 그림이 아니라,
원문에서 확인한 문제·구성·직접 선행 관계를 우리 비교 질문에 맞춰 정리한 것이다.
자세한 저자별 비교군은 문헌 상세에서 확인한다.

### 3.2 DiagMLP 결과에서 배울 점과 과장하면 안 되는 점

논문 v2에서는 Eadro 기반 결과의 변화가 크지만 TVDiag/DeepHunt 기반에서는
대체로 비슷한 성능을 보고했다. 일부 Top-k는 낮고 표의 불일치도 있다. [S03]
따라서 배울 점은 “GNN은 쓸모없다”가 아니라
**복잡한 모델을 제안하기 전에 기존 전처리와 단순한 결합 기준의 기여를 분리하라**는 것이다.
우리 모델의 전체 파라미터 수도 DiagMLP가 더 많으므로 MLP라는 이름만으로 경량성을 주장하지 않는다.

### 3.3 추가 국내외 조사 결과

기존 중심 목록 외에 MicroHECL·TraceRCA·MicroRCA·CausalRCA·LatentScope·LagRCA 등을 확인했다.
국내 관련성은 다음처럼 구분했다.

| 연구 | 확인한 발표·소속 | 우리 주제와 관계 | 확보 수준 |
|---|---|---|---|
| **AnoProp** | KAIST, 정보과학회논문지2025 | 공유자원 전파와 원인 순위. 직접적인 국내 선행 | 원문 확인 |
| **HERO** | KAIST, 국제 ICWE2025 poster | root 라벨 없이 이종GNN으로 진단한다는 접근 | 서지·초록만; 데이터/실험 미확인 |
| **GRAFlow** | 아주대 소속 참여 국제 공동연구,2026 | 모달 결합·다중 scale 그래프 진단 | 본문 mirror 확인; 수치·split 주의 |

**국내에 비슷한 연구가 없다고 주장할 수 없다.**
반면 국내 소속이라는 이유만으로 모두 같은 서비스 순위 비교군에 넣어서도 안 된다.
특히 AnoProp의 service/pod/node 혼합 출력은 우리27서비스 후보와 매핑이 필요하다. [S15–S18]

### 3.4 관측 비교와 MLP 방향에서 가까운 최신 선행

별도 기존 조사 기록까지 대조하여 **PRISM(2026-01 preprint)**과
**controlled MLP/PSC-GRCA(2026-09 preprint)**를 원문으로 추가 확인했다.
전자는 내부 자원과 외부 증상 점수를 구분하고, 후자는 상대 특징·대상 빈도 prior·
그래프 기여를 통제한다. 따라서 “그래프 없는 순위”, “상대 정보를 쓰는 작은 MLP”만으로
새 기여라고 주장할 수 없다. [S19,S20]

이는 MLP 연구를 포기해야 한다는 뜻이 아니다.
**어떤 확인된 오류 조건에서 기존 구성보다 무엇이 달라지고, 그 차이가 효과를 내는지**
명확해야 한다는 뜻이다. 두 논문의 수치를 우리 결과와 직접 비교하거나 실행 검증한 것으로 쓰지 않는다.

입력·모델·학습·분할이 함께 달라졌기 때문이다.

#### 이미 완료한 자체 MLP 실험을 별도로 보존해야 한다

서비스별 정상 대비 변화만 보는 `local`과, 같은 사건의 다른 서비스 평균 대비
상대 차이를 추가한 `relative`를 비교했다. 두 모델은 공유 MLP32→16→1,
총3457파라미터이며 관측 mask/비율을 공통으로 사용했다.
다만 local의0입력 연결은 학습에 기여하지 않으므로 파라미터 수가 같다고
유효 표현 용량까지 동일한 것은 아니다.
로그/Hawkes/시간열 인코더를 사용하는 출판 모델의 복원이 아니라 **독립적인 자체 방법**이다.
최대200epoch·조기종료 규칙으로 SN/TT×두 모델×3seed=12회 학습·예측 재현을 완료했다. [L07]

| 당시 창 분할 개발 평가 | local Top1 | relative Top1 | 차이 |
|---|---:|---:|---:|
| SN |80.42%|89.35%|+8.93%p|
| TT |71.15%|75.08%|+3.93%p|

같은 기록의 외부 DiagMLP 복원 참고값은 SN95.52%/TT98.80%로 더 높았다.
후속 점검에서 이 외부 참고가 `calibration200` 결과임을 확인했다.
해당 `split.json`에는 SN 검증28사건과TT 검증81사건 전부가 TRAIN에도 포함된다고 기록돼 있다.
다만 입력·목적이 달라 차이 전체를 한 구조의 효과로 돌릴 수 없다.
같은 사건의 다른 창이 학습에 포함된 창 분할이므로 독립 사건 일반화도 아니다.
따라서 **그 창 분할 안의 점수 차이는 확인했지만, 이를 새 사건의 상대 정보 효과로 인정할 수는 없다.
출판 방법 대비 우위·신규성·같은 정확도의 효율도 확인하지 못했다.**
이후 사건 분할의86.56%와75.08%를 연결해 성능이 오르거나 내렸다고 말하지 않는다.

### 4.2 현재 TT 실험의 정확한 범위

| 항목 | 실제 사용한 조건 |
|---|---|
| 자료 | 공개 Train Ticket 자료의 허용 개발 부분 |
| 정답·후보 | 주입 사건81개, 업무 서비스27개, CPU/지연/손실 각27사건 |
| 시간 표본 |10초 창4069개=장애3451+정상618 |
| 분할 |3fold. fold마다54사건 학습/27사건 검증 |
| 검증의 의미 | 같은 서비스의 두 고장 유형으로 학습하고 나머지 유형을 검증 |
| 반복 |seed11/23/37, 모델별9회 |
| 입력 |지표7채널, 평균 latency, Drain/Hawkes 로그; count는 기준 모델에 미투입 |
| 학습 |Adam .001, batch256,200epoch; validation 공동 loss 최솟값 선택 |
| 평가 |사건 동일 가중 Top1/Top3/MRR, 장애 유형별 결과,seed 변동,비용 |
| 보호 범위 |원본test1744창과unassigned1행 제외; 추가 데이터의 최종 관측·예측 미사용 |

**새 서비스나 학습 전체에 없던 고장 유형을 시험한 것은 아니다.**
서비스와 고장 유형은 각각 학습에 등장하지만, 해당 서비스와 특정 고장 유형의 조합을 검증한다.
또한 recording이 공유되므로 새로운 수집 환경 평가가 아니다.
원 Eadro 논문의162회 TT 주입과 공개 자료에서 확보한81사건도 구분해야 한다. [L02,L06]

### 4.3 기준 모델 결과

아래는 **복원 기준 모델을 우리 설정으로 학습하고 모델 선택에 사용한 validation에서 평가한 결과**다.
제안 모델의 점수나 독립 최종 성능이 아니며 원 논문 수치와 직접 비교하지 않는다. [L03]
원 DiagMLP v2의TT Top1/Top3는98.5/99.7%다. 현재99.74%만으로 더 좋아졌다고 말할 수 없다.
추가 relative/count/ensemble은 적용하지 않았지만200epoch·층폭·dropout·분할·집계는 선언된 우리 설정이다.

| 모델 | Top1 | Top3 | MRR |
|---|---:|---:|---:|
| DiagMLP 복원 기준 | **86.56%** | **99.74%** | **0.9303** |
| Eadro 복원 기준 |19.67%|39.85%|0.3442|

DiagMLP의 고장 유형별 결과:

| 유형 | Top1 | Top3 |
|---|---:|---:|
| CPU 부하 | **77.81%** |99.58%|
| 네트워크 지연 |90.09%|99.68%|
| 네트워크 손실 |91.80%|99.95%|

DiagMLP의 seed별 전체 Top1은82.57/88.76/88.37%다.
반복 학습 간 변동이 있으므로 평균 한 값만으로 안정성을 주장하지 않는다.

**해석할 수 있는 것:** 현재 조건에서는 정답이 상위3개에 대체로 들어가지만
첫 번째로 선택되지 않는 오류가 남으며, CPU에서 그 차이가 크다.

**해석할 수 없는 것:** 이를 곧바로 전파 혼동, 정보 부족, 정규화 실패,
특정 head의 결함 중 하나로 확정할 수 없다. 오류의 위치와 발생 메커니즘은 아직 다르다.

Eadro는9회 중5회에서 epoch1 모델이 선택됐다.
일부 validation 입력은 TRAIN 정규화 범위를 크게 벗어났다.
산술은 확인했지만 이 현상이 오답을 유발했다는 인과관계는 분리하지 못했다.
따라서19.67%를 이용해 DiagMLP나 향후 제안 모델의 보편적 우월성을 주장하지 않는다. [L01,L03,L05]

### 4.4 관측 개수 보완을 왜 멈췄는가?

공개 입력 경로에서 mean latency만 전달되고 count가 빠진다는 사실은 확인했다.
그러나 **정보가 버려진다는 사실과 그 정보가 진단에 필요하다는 사실은 다르다.**

network 자료에서 count 양수 집합과0 집합의 Top1 차이는
seed별 **+3.47/−2.99/−10.71%p**였다.
사전 조건은 +5%p 이상이3개 seed 중2개 이상이었는데0개였다. [L04]

그래서 추가 count 모델과 같은 폭의 zero-count 대조를 **학습하지 않았다.**
“추가했더니 효과가 없었다”는 결과가 아니다.
부분집합의 사건 구성이 다르므로 “기록이 없을수록 좋다”는 결론도 아니다.
모든 count 활용법을 반증한 것이 아니라, 이 후보를 지금 추진할 근거가 부족했다.

### 4.5 완료를 뒷받침하는 검증과 비용

- 기존 기록: 집중 검사20개, 기준18회와 저장 checkpoint의 예측 재현 통과.
- 별도 점수 계산: TRAIN/validation 예측36파일, 사건/부분집합972개와 요약20개 대조.
- 같은 버전의 유효한 증거를 이번 조사에 재사용했다. 이번에 재학습한 것이 아니다.
- 준비234.81초, 기준18회 최대3개 병렬 실행의 실제 경과109.36분.
- 전체 파라미터: DiagMLP140,033/Eadro66,178. MLP가 무조건 더 작은 것은 아니다.
- 입력 준비를 제외한 fold 전체 추론 중앙값은0.704/0.804초다.
  이는 약1335–1368창의 batch 평가이지, 실제 장애1건의 종단간 응답시간이 아니다. [L01,L05]

## 5. 남은 질문과 연구 방향

### 5.1 목표는 유지하되 해결책은 아직 정하지 않는다

현재의 적절한 연구 질문은 다음과 같다.

> **방법론에 충실한 기준 모델이 실제 원인을 낮게 순위화하는 반복 조건은 무엇이며,
> 그 조건에 대응하는 한 변경이 같은 정보·평가 조건에서 첫 후보의 정확도를 높이는가?**

“관측이 부족해서 틀린다”나 “전파 피해를 원인으로 착각한다”를 문제의 확정 원인으로 쓰지 않는다.
전자는 현재 추진 근거가 부족하고, 후자는 산업 선행연구에 존재하지만 우리 오류에서 확인하지 않았다.
높은 Top3만으로 별도 reranker를 정답으로 선택하지도 않는다.

### 5.2 CPU 점검은 한 선택지이며, 주 자료의 실패 조건을 먼저 확정한다

CPU는 현재 TT에서 눈에 띈 오류이지 유일한 연구 문제가 아니다.
다음 협의안은 RCABench1422 전체의 평가 계약을 정하고, 그 자료의 기준 결과에서
반복되는 오류를 선택하는 것이다. 기존 TT에서는 아래 보조 점검이 가능하다.

1. 실제 원인은 몇 위이고, 대신1위로 올라간 서비스는 무엇인가?
2. 같은 오답 후보가 seed·사건에 걸쳐 반복되는가?
3. 실제 원인과 잘못 고른 후보의 원 관측·변환된 관측·학습 범위는 어떻게 다른가?
4. 같은 고장 유형의 정답 사건과 비교했을 때 구별되는 조건이 있는가?

이 단계는 원인을 찾기 위한 비교다. 몇 개의 눈에 띄는 창으로 전체를 설명하지 않는다.
특정 조건이 확인되면 그 조건을 다루는 기존 방법의 구성과 먼저 대조한다.
반복되는 조건이 없다면 새 모듈을 추가하지 않고 문제 정의를 더 좁힌다.

### 5.3 확인 결과에 따른 진행·중단 기준

| 단계 | 필요한 산출물 | 다음 단계로 갈 조건 |
|---|---|---|
| 오류 조건 확인 |사건별 오답 후보·원인 순위·관측 비교|반복되는 구별 조건이 있고 단순 라벨/처리 오류가 아님|
| 변경 하나 선택 |해당 조건과 변경의 연결, 기존 방법과 차이|기존 count/masking/scorer의 이름만 바꾼 제안이 아님|
| 개발 대조 |기존 모델 vs 변경 모델, 필요한 용량/정보량 대조|전체 Top1·MRR 개선과 유형별 악화·비용을 함께 평가|
| 독립 확인 |선택에 사용하지 않은 사건/recording 또는 호환 외부 자료|자료 독립성과 정답·입력 호환성이 확인됨|
| 주장 확정 |실험 조건·효과 크기·변동·한계|주장 범위가 실제 평가 범위를 넘지 않음|

최소 개선 폭·허용 악화·비용 상한은 다음 실험 전에 정한다.
이전 count 후보의 기준을 결과에 맞춰 바꾸거나 다른 후보에 무조건 재사용하지 않는다.
CPU 오답을 먼저 분석하더라도 실제 추론에 정답 고장 유형을 알려주는 방식으로 바꾸면 안 된다.
개선 평가도 정답이 Top3에 들어온 사건만 골라 수행하지 않는다.

## 6. 데이터 확장: 무엇이 준비됐고 무엇이 후보인가?

새 데이터는 “자료가 크다”보다 정답·관측·독립성이 현재 질문에 맞는지가 중요하다.

| 자료 | 역할·후보 범위 | 아직 남은 조건 |
|---|---|---|
| **RCABench** |확보1422사례 전체를 주 데이터 우선 후보로 검토|정답 의미·관측·독립 그룹·평가 계약.369/350을 자동 선정 기준으로 쓰지 않음|
| **RCAEval RE2-OB/TT** |180사례,60반복그룹. 표준 비교 자료|봉인 분할과 반복그룹 유지, 자료에 맞는 타당한 입력 처리|
| **RCAEval RE3-OB/TT** |60사례를 추가 확보 후 코드 장애 검증 후보로 사용|RE2와 별도 묶음. 아직 확보·학습 완료로 쓰지 않음|

RCABench369단일 항목과350최소관측 통과수는 감사 통계이지 연구 자료의 상한이 아니다.
두 항목1053건 역시 독립된 두 물리적 원인이라 단정하지 않는다. 주입 규칙의 expected-impact일 수 있다.
caller/callee가 모두 정답이면 원인/피해 구별을 검증할 수 없는 경우가 있으므로 정답 의미를 먼저 정한다.
기존9채널을 그대로 만들기 어렵다는 이유나 정답trace가 없다는 이유로 사례를 자동 제외하지 않는다.
주입으로 관측이 사라진 사례를 삭제하면 평가가 쉬워질 수 있다.

trace가 필요한 현재 주 실험에서는 trace 없는 Sock Shop과 metric-only RE1을 제외한다.
이는 자료 자체가 부적합하다는 뜻이 아니다. 전체 확보와 전부 같은 방식으로 학습하는 것도 다르다.
GAIA와OpenRCA는 선정·가공·학습 완료 자료가 아니다.
일부 라벨을 다른 규칙으로 해석하면 후보 수가 달라지므로 수량을 늘리는 것 자체가 목적이 아니다.
기존 SN/TT 사건들은 이미 개발·학습에 사용됐다. 따라서 봉인된 원본test의 **창**을
나중에 열더라도 미접촉 최종 **사건**이 되는 것은 아니다.
자료 선택은 정답 단위, 시간 범위, 실제 모달 지원, 반복 그룹, 입력 의미를 먼저 확인한 뒤 한다. [L10–L12]

## 7. 실현 가능성·미확인 사항·명확한 한계

### 7.1 실현 가능성이 있는 부분

- 입력 준비·학습·선택·점수 검증 체계가 이미 작동했다.
- 실제 원인을 후보 상위에 포함시키는 기준이 있으므로, 첫 후보 오류를 좁게 분석할 수 있다.
- 반복 가능한 작은 변경과 대조 실험을 수행할 계산 비용이 확인됐다.
- 관련 국내외 방법이 있어 새 구성의 중복성과 비교 조건을 점검할 수 있다.

따라서 **제한된 정량 개선 연구를 수행할 기반은 있다.**
보유한 전체 자료가 무조건 부족하다는 판정이 아니다.
현재 부족한 것은 주장의 범위에 맞는 독립 평가와 확정된 정답·분할 계약이다.
이는 새로운 알고리즘의 성공·독창성·논문 채택 가능성을 확정한다는 뜻이 아니다.

### 7.2 아직 확인해야 하는 부분

| 미확인 항목 | 필요한 증거 |
|---|---|
| 주 자료의 반복 오류 조건 |장애 유형·정답·관측 상태별 확인. TT CPU 오류는 보조 점검 대상|
| Eadro 낮은 결과의 해석 |구현 충실도와 별개로 분할·스케일·선택 현상을 구분|
| 향후 선정할 변경의 추가 효과 |동일 조건 대조와seed/사건별 차이; 이전relative 개발효과와 구분|
| 새 구성의 기여 |가장 가까운 기존 구성 대비 실제 차이|
| 독립 자료에서도 유지되는가 |새 사건/recording 또는 입력 호환 외부 자료|
| 현장 조사·복구에 도움이 되는가 |운영자 조사시간/실제 적용 평가; 현재는 측정하지 않음|

### 7.3 이미 명확한 한계

1. **개발 자료 재사용:** validation으로 checkpoint를 선택하고 그 점수를 보고했다. 기존SN/TT 사건은 이미 개발에 사용되어 독립 최종 사건으로 다시 지정할 수 없다.
2. **분할 범위:** 새로운 서비스·새 환경의 일반화가 아니다.81사건과3seed를243독립사건처럼 세면 안 된다.
3. **고장 범위:** 현재는CPU·지연·손실 주입이다. 논리 버그·동시 복수원인·실제 운영 전체를 대표하지 않는다.
4. **인과 정답 부재:** root 서비스 라벨은 전파 edge의 인과 정답이 아니다. attention이나 호출 관계를 인과 증명으로 제시할 수 없다.
5. **처리 한계:** Hawkes7845계산 중5585가50회 상한에 도달했다. 유한값·경고 없음은 확인했으나 수렴을 입증하지 않았다.
6. **스케일 범위 차이:** 일부 validation 값이 TRAIN 범위를 크게 벗어났다. 계산 오류가 아니라는 확인과 오류 원인 규명은 별개다.
7. **외부 비교 한계:** 원 논문/다른 연구의 수치를 우리 사건 균등 평가와 직접 비교할 수 없다.
8. **문헌 접근 한계:** HERO/KubeIn 등은 초록 수준이다. 국내외 전수조사를 완료했다는 주장도 하지 않는다.

**판정:** 실제 문제의 존재와 실험 수행 기반은 확보했다.
그러나 기존 방법보다 나은 새 기여와 독립 자료의 효과는 아직 확인하지 못해 논문 기여 판정은 보류다.
효과가 단순 통계 점수·대상 빈도·기존 상대 특징으로 설명되면 그 설명을 받아들이고,
더 복잡한 모듈을 붙여 성과처럼 만들지 않는다.

## 8. 동료 연구원에게 전달할 최종 판단

**우리가 선택한 것은 ‘기록 개수를 추가하는 모델’ 자체가 아니라 ‘원인 서비스의 조사 우선순위를 개선하는 문제’다.**
관측 개수는 그 목표를 위한 후속 후보였고, 추진 근거가 부족해 멈췄다.

지금까지 확보한 것은 자체 MLP의 과거 창 분할 내 점수 차이 기록,
방법론에 충실한 비교 모델, 검증된 입력·평가 체계, 현재 조건의 구체적 첫 후보 오류다.
확보하지 못한 것은 그 오류의 반복 원인, 강한 기존 방법 대비 개선, 독립 평가에서의 추가 효과다.

**따라서 다음 협의안은 RCABench 전체 후보에 대한 정답·관측·분할 계약을 정하고,
해당 조건의 기준 평가에서 좁은 오류 조건을 찾는 것이다.**
기존 TT CPU 분석을 전체 연구 주제로 고정하지 않는다.
조건이 확인되면 관련 선행 구성과 대조해 한 변경을 시험하고,
확인되지 않으면 새 아이디어를 억지로 붙이지 않는다.

이 보고서와 후속 설명 작성 중 새 모델 학습·추가 성능 실험·보호 관측자료 접근은 하지 않았다.
모델 코드·원자료·동결 계약·과거 성능 결과도 바꾸지 않았다.
문헌과 기존 기록을 대조하고 이 인수인계 문서의 용어·해석·자료 역할을 정정했다.
