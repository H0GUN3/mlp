## 확인할 사항

1. 네 점수 기준 각각의 유효 평가 사례 수가173인지, 사례/그룹/창 중 어느 단위로
   평균했는지 확인한다. 점수가 결측인 후보와 평가에서 빠진 사례를 혼동하지 않는다.
2. 최상위 동점 집합을 T, 그 안의 허용 정답 수를 g라 하면 Top1 credit은 g/|T|다.
   저장된 모든 후보의 점수·결측 순서를 직접 읽어 이를 독립 재계산한다.
   주입 설정이나 정답은 채점에만 사용하며 점수를 다시 만들지 않는다.
3. 기준×정답 계약마다 사례 수, credit 합, 평균, credit0/부분/1 사례 수,
   최상위 동점 사례 수를 표로 남긴다.
   56.65%≈98/173,57.23%≈99/173이라는 사용자의 산술 관찰과 HTTP 소수 credit을 확인한다.
4. 같은 점수의 두 정답 계약 및 HTTP/span 기준의 우열 반전을 명시한다.
   설정 표적 하나가 자동으로 더 올바른 정답이라고 결론 내리지 않는다.
5. 현재 ops-lite 설명의 `also_accept`와 고정 RCABench 관련 생성 코드의
   expected-impact 서비스 목록을 구분한다. 현재 배포 설명을 과거 RCABench
   아카이브 생성 규칙에 그대로 소급하지 않는다.
6. RCAEval240은 RE2-OB90+TT90, RE3-OB30+TT30인지 기존 저장 인덱스 집계로 확인한다.
   기존 감사 시점의 관측 확보180/미확보60과240개 메타데이터 확인을 구분한다.
   이후 작업의 준비 산출물과 기존 관측자료 확보 여부를 혼동하지 않는다.
7. ops-lite197건의 메타데이터 일치와 관측을 비교한8사례/80개 비어 있지 않은
   파일 해시 일치는 기존 근거로 재사용한다.197건 전체 관측 일치라고 확대하지 않는다.

## 읽기·쓰기와 DAG

1차 wave의 독립 구성요소는 **채점 산술 / RCAEval 구성 / 정답 의미** 세 가지다.
전부 완료되면 검증·보완 보고 노드가 인계 문서를 읽고 최종 설명을 작성한다.
wave 폭3은 기본 동시 실행 한도5 이내다.

| 노드 | 경로 분류 | 쓰기 범위와 인계 |
|---|---|---|
| scoring | quick: 저장된 점수의 기계적 기대 credit 재계산 | scoring_check.py, scoring_check.json, SCORING.md |
| inventory | quick: 기존 집계와 manifest 대조 | INVENTORY.md |
| semantics | unspecified-low: 버전별 정답 의미가 같다고 할 수 있는지 판단 | LABEL_SEMANTICS.md |
| verify-report | unspecified-low: 숫자·근거를 연결하고 범위 과장을 판별 | REPORT.md, VERIFICATION.md |

점수 재계산 코드는 표준 라이브러리만 사용하고 작은 assert 자체 검사를 포함한다.
원래 실험은 재실행하지 않는다. JSON 결과는 새 경로에 exclusive-create한다.
각 노드는 자기 파일만 쓰고 공유 원본을 변경하지 않는다.
보고 노드가 읽는 인계 문서는 위 파일 그 자체이며 별도 완료 표식 파일은 만들지 않는다.

## 검증과 종료

원래 결과 SHA256과 새 재계산 코드 SHA256, 실제 계산 명령 exit0, 재계산 최대오차,
173사례별 credit 대조, 작은 동점·결측 자체 검사 통과를 확인한다.
마지막 노드는 저장된 후보에서 적어도 HTTP 부분 credit 사례와 span 단일 정답 사례를
독립 확인하고, 두 기준·계약 평균 및240의 구성 표를 대조한다.
문헌 설명은 해당 URL/고정 코드와 로컬 검수 경계를 연결한다.
완료 알림이 아니라 이 증거를 읽고 판정한다.

최종 문서에 각 점수의 **분모·평균 단위·동점 규칙**을 한 줄로 명시한다.
TT는 기존 기준 유지, SN은 비교 조건·반복 오류 분석, RCAEval은 후속 비교,
RCABench는 조건부 확장, ops-lite는 중복을 고려한 추가 자료라는 역할을 유지한다.
TT/SN의 최신 실험을 재실행하거나 옛 진행 상태를 현재 상태로 잘못 표현하지 않는다.
33개 테스트 통과는 구현·계산의 증거이지 정답 의미·DiagMLP 진단 성능의 증거가 아니다.
